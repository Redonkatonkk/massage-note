# 产品与业务规则

> 状态：当前产品规则 · 适用版本：`0.12.26`
> 实现细节以 [`ARCHITECTURE.md`](ARCHITECTURE.md)、[`API.md`](API.md)、Prisma schema、共享契约和自动化测试为准。

本文整理 Massage note 的产品范围、角色权限、记工与财务口径。它说明“系统应该做什么”；接口字段、代码位置和部署步骤分别由 API、架构和部署文档负责。

## 1. 产品目标

开发一套多店铺使用的按摩店记工与财务管理系统，替代纸质手写记工表。主要使用设备为手机，同时支持 iPad 与电脑。系统必须简单、清晰、适合年龄较大的员工使用，并保证财务计算准确、历史数据可追溯、多设备实时同步。

## 2. 核心原则

1. 旧记录像写在纸上一样永久保留当时内容，不因后续项目、价格、提成比例或折扣模板修改而变化。
2. 所有金额使用整数美分存储，避免浮点误差；所有页面、AI 答复和个人日结图片中的只读金额统一四舍五入显示为整美元，不显示小数点，且不得改变底层账本值。金额编辑框不再自动补 `.00`，遇到既有真实美分时仍保留其精确值，避免编辑即改账。
3. 所有关键修改保留审计历史。
4. 所有删除使用软删除。
5. 折扣由店铺承担，不减少员工工资。
6. 现金大费、刷卡大费、现金小费、刷卡小费必须分别保存具体金额。
7. 财务由后端确定性计算，AI 只负责理解自然语言和调用受限工具。
8. 系统支持多店铺、多角色、多设备同时登录与实时同步。
9. 第一版以响应式 Web 应用为主，不提供浏览器安装入口；后端 API 与业务逻辑必须可复用于未来 iPhone/iPad 应用。
10. 界面支持简体中文和英文；没有本机语言偏好时默认使用简体中文，用户可在登录、断网、帮助和全部业务页面随时切换，选择在本机持久保留。英语界面对店铺自定义的中文主要项目、加项和折扣名称自动显示领域英译，但编辑时保留原始中文，不得因切换语言改写历史快照。

## 3. 用户与角色

### 3.1 角色

- Owner：拥有者，每家店唯一。
- Manager：经理，与拥有者基本同权，但不能修改拥有者、转移拥有者身份或删除店铺。
- Employee：员工。

角色按店铺维度保存。同一用户可以在不同店铺中拥有不同角色。

权限角色与是否参与记工相互独立：

- Owner、Manager、Employee 均可设置为“参与记工”或“不参与记工”。
- 参与记工的拥有者和经理与普通员工一样出现在今日表格中，并拥有自己的项目提成、记工、小费和财务统计。
- 参与记工的经理按普通员工方式进入工资结算和“老板尚欠员工”计算。
- 参与记工的拥有者仍计算项目工资和小费，供经营核算使用，但不进入“老板尚欠员工”或给自己的工资结算；界面单独显示为“拥有者本人服务收入”。

### 3.2 拥有者权限

- 管理所有记工与历史记录。
- 管理员工、经理、加入申请。
- 只填写名字即可预先创建尚未注册账号的新员工。
- 管理项目、额外项目、折扣项目、提成规则。
- 查看全部财务。
- 进行日结、取消日结、现金结算、工资结算。
- 修改店铺设置。
- 删除店铺。
- 转移拥有者身份。

### 3.3 经理权限

与拥有者几乎同权，但不能：

- 修改、移除或降级拥有者。
- 转移拥有者身份。
- 删除店铺。

经理可以指定其他经理。

经理也可以只填写名字预先创建新员工。

### 3.4 员工权限

员工可以：

- 查看当天所有员工的记工。
- 为自己或其他员工新增、修改、删除当天记工。
- 查看所有当天记录详情和公开备注。
- 在今日页面通过营业日日历查看自己任意过去营业日的记工；历史响应只包含本人行、班次、记工和本人小计。
- 使用记工 AI 助手。
- 查看自己的全部历史财务。
- 查看自己的工资结算记录和老板尚欠金额。
- 查看自己的现金结算状态。
- 从今日员工行或财务页查看自己的个人日结，并生成与设备屏幕比例一致的 PNG 图片。

员工不能：

- 修改过去营业日记录。
- 查看其他员工历史财务。
- 管理店铺设置、项目、成员、结算与全店日结。
- 查看其他员工或全店日结信息。

## 4. 登录与账号

### 4.1 登录方式

- 使用 Firebase Authentication 手机号验证码登录。
- 仅支持美国手机号。
- UI 输入 10 位美国号码，内部标准化为 E.164，例如 +14701234567。
- 支持同账号多设备同时登录。
- 默认长期保持登录状态。
- 支持退出当前设备和撤销所有设备会话。
- 暂不支持更换手机号和账号恢复。

### 4.2 短信防刷

- 仅允许 +1 国家码。
- 重发验证码倒计时。
- 同号码、同 IP 频率限制。
- 连续错误临时锁定。
- Firebase reCAPTCHA。
- 不泄露号码是否已注册。
- 开发环境使用测试号码。

### 4.3 首次注册

所有用户填写：

- First Name
- Last Name

通常仅显示 First Name 或店铺内 Display Name。

## 5. 多店铺与加入流程

### 5.1 创建店铺

拥有者首次创建店铺时填写：

- 店铺名称。
- 六位数字店铺 ID。

店铺 ID 由拥有者自己输入，必须全局唯一，被占用时要求重新输入。

创建后直接进入店铺设置向导，而不是空白主页。

### 5.2 店铺设置向导

1. 店铺名称。
2. 六位店铺 ID。
3. 店铺时区：默认提取拥有者设备时区，可修改。
4. 营业日截止时间：默认 22:00，可修改。
5. 店铺全局默认提成比例。
6. 主要项目。
7. 额外项目。
8. 折扣项目。
9. 确认并进入今日主页。

店铺设置页还提供“周一至周四自动折扣”：Owner 或 Manager 可开启规则，设置折前大费应用门槛和固定折扣额度。系统按营业日判断星期，在主要项目与额外项目之和达到门槛时自动添加一项折扣快照。自动折扣可与其他折扣同时存在，由店铺承担，不降低员工大费工资；配置变化不批量改写历史记工。用户可在记工详情中只为当前记录直接移除自动折扣，无需二次确认；该选择会持久保留并可恢复，不会关闭全店规则。

### 5.3 加入店铺

员工输入六位店铺 ID 后：

1. 显示店铺名称。
2. 员工确认。
3. 如果账号注册时填写的 First Name 与本店一个待认领员工的名字相同，系统直接把账号绑定到原成员关系；原成员 ID、记工、提成和财务历史全部保留。
4. 没有匹配项时提交加入申请。
5. 拥有者或经理审批。

### 5.4 显示名与同名限制

- 当前在职成员的店内显示名不得重复，不区分大小写。
- 内部始终使用唯一用户 ID。
- 拥有者可修改员工显示名。
- 已离职员工保留历史名称和记录。
- 拥有者或经理预先创建员工时只填写名字，不要求姓氏或手机号；该成员在账号认领前也可参与记工和配置提成。
- 自动认领只使用账号注册资料里的 First Name 与本店待认领员工名字进行规范化精确匹配，不能靠在加入表单中输入他人的名字冒领。

### 5.5 离职与重新加入

移除员工时：

- 保留全部历史记工、财务和审计。
- 仅停用当前成员关系。
- 重新加入时恢复关联。

## 6. 店铺与营业日

### 6.1 营业日截止

默认 22:00，可修改。

记录归属按开始时间判断：

- 截止时间前开始，属于当前营业日。
- 截止时间后开始，属于下一营业日。
- 跨越截止时间结束，不改变归属。

### 6.2 历史日期

拥有者和经理可通过日历切换任意营业日，查看并修改当日主表格。员工也可在今日页面切换过去营业日，但只读取自己的行、班次、记工和本人小计，不能修改历史；员工财务页面同样只显示本人历史。

已日结营业日的修改规则：

- 日结后员工不能再修改当日记工。
- 拥有者或经理必须先取消日结，才能修改当日记工。
- 如果该营业日的现金结算已经结清，取消日结或修改记录时，相关现金结算自动恢复为“未结清”，并要求重新确认。
- 已存在的工资结算账本不自动删除；系统根据修改后的记工重新计算尚欠金额，并明确提示“结算后历史数据发生过修改”。
- 修改、取消日结、现金结算状态回退及重新结算均写入审计日志。

## 7. 项目配置

主要项目、额外项目和折扣项目在管理页分为三个独立区域，不使用跨类型的顶部集成表单。各项默认显示名称、价格、时长、默认提成和启用状态摘要，点击“修改”才展开带标签的编辑栏；每类新增表单也默认收起并由分类标题处单独打开。额外项目的名称、简称、金额、时间、默认提成、启用状态和保存操作在桌面宽度下保持一条紧凑横栏，窄屏再按断点换行。三类项目均可独立上移、下移，保存后的顺序用于项目管理、快速记工和详情选择。

### 7.1 主要项目字段

- 完整名称。
- 主表格简称。
- 一个或多个“时长 + 价格”档位；同一项目内时长不能重复。
- 默认提成比例，可为空。
- 排序。
- 启用状态。

例如一个 `Body Massage` 项目可以同时设置：

- 30 分钟 / $60
- 60 分钟 / $100
- 90 分钟 / $150

价格由店铺按项目和时长分别设置，无需为每个时长重复创建项目。项目默认提成、员工项目专属提成、排序和启用状态属于项目本身，所有时长档位共享。

### 7.2 额外项目

字段：

- 名称。
- 简称。
- 默认金额。
- 默认时长，可为空。
- 默认提成比例，可为空。
- 排序。
- 启用状态。

一条记工可选择多个额外项目，员工可修改本次金额或添加自定义额外项目。

### 7.3 折扣项目

- 仅固定金额，不支持百分比。
- 一条记录可使用多个折扣。
- 员工可使用预设折扣，也可自定义名称和金额。
- 用户输入正数，内部按减免处理。
- 折扣不需要审批。
- 折扣由店铺承担，不减少员工工资。
- 周一至周四自动折扣与普通折扣使用同一折扣总额规则，但由系统根据店铺门槛自动生成和重新判断；记工详情可为单笔记录持久移除或恢复自动折扣。
- 支持独立排序和启用状态。

### 7.4 提成优先级

1. 某员工对某项目的特殊比例。
2. 该员工默认比例。
3. 该项目自身默认比例。
4. 店铺全局默认比例。

每条记录保存最终生效比例快照。
保存员工默认或员工项目专属提成时，系统会按最新完整优先级重算该员工未日结的当前营业日记工，并同步刷新今日小结、个人日结及相关现金工资字段；若现金已经结清则自动回退为待结清。已日结营业日和更早历史记录不得改写。

自定义主要项目和自定义额外项目没有项目默认比例，按以下顺序取值：

1. 该员工默认比例。
2. 店铺全局默认比例。

员工不能在记工时自行修改提成比例。拥有者或经理可以修改本单最终比例，但必须保存修改前后数据和审计记录。

## 8. 今日主页面

- 营业日日历选择日期后立即加载目标日期，不保留额外“查看”按钮。
- 全店“大费总额、折扣总额、礼物卡销售、礼物卡核销支出、店铺收入”汇总只向拥有者和经理展示，普通员工不显示该区域；顶部今日汇总不单独显示小费总额，但店铺收入公式仍包含小费。
- `店铺收入 = 折后大费业绩 + 小费总额 - 员工总收入 + 礼物卡销售实际收款 - 礼物卡核销支出`，其中 `礼物卡核销支出 = 礼物卡大费 + 礼物卡小费`，由后端按整数美分计算。卖卡实际收款全部算店铺收入，不进入任何员工提成、工资或现金结算；客人使用礼物卡付款全部算店铺支出。

- 财务汇总的付款方式默认选择全部。店铺级汇总和日结合计中的全部项目数量等于记工数量加礼物卡销售张数，客人总付款等于记工实收服务费、小费与礼物卡销售实际收款之和。每日小计不显示全部项目数、记工数、实收服务费、小费或客人总付款，营业日后的第一项固定为 `今日流水 = 折后大费业绩 + 礼物卡销售实际收款 - 礼物卡核销支出`。员工小计不分摊礼物卡销售；明确限定员工、仅大费、仅小费或仅高亮记工时，也不纳入店铺级卖卡记录。

### 8.1 桌面与 iPad 横屏

- 每行一名员工。
- 每个格子一条记工。
- 左侧固定员工姓名。
- 中间横向显示记录。
- 右侧显示当日统计。
- 大费、小费和应得使用独立标签与金额行，长金额不得粘连、裁切或被悬浮按钮遮挡。
- 行末提供空白“+”格子。
- 支持横向滚动。
- 支持拖动整行排序。

### 8.2 手机竖屏

- 每名员工使用折叠卡片或纵向区域。
- 记工卡片在员工区域内紧凑横向排列，可左右滑动查看全部记录。
- 新增记工入口跟随在横向卡片队列末尾。
- 不强行压缩桌面表格。
- 页面和弹窗不得产生横向漂移；页面根节点覆盖动态视口高度并限制下拉边界，不能在底部露出大块空白区域。

### 8.3 员工进入今日表格

- 拥有者或经理可手动添加员工。
- 在成员管理中只填写名字即可创建员工；未注册员工会标记为“等待注册”。
- 成员管理的短信接收号码在没有专用覆盖值时自动填入已关联账号的注册手机号。开启“接收个人日结短信”时，专用号码和注册手机号至少要有一个有效值；两者均为空时不得保存，并向店长明确提示先填写号码或让员工完成账号注册。
- 参与记工的普通员工若尚未出现在当天表格，可在当前营业日点击“上班”把本人加入；不能借此添加其他成员。
- 可从今日表格隐藏员工；其记录同时隐藏但不删除、不影响财务。
- 重新显示员工时，记录恢复；店主或经理在营业日已日结后仍可调整显示状态，不改变记工、日结快照或财务。
- 每天默认按加入顺序出现，老板每天可重新拖动排序。
- 排序实时同步，记录随员工整行移动。

### 8.4 工作状态

- 今日记工页面只为尚未加入当天表格的普通员工提供“上班”按钮，不提供“下班”按钮。
- “上班”只负责建立本人当天班次并加入今日表格；员工行的可见工作状态不依赖班次结束时间。
- 员工行根据当前时间是否落在记工的开始与结束时间内显示状态。
- 没有进行中的记工显示“空闲”；有进行中的记工显示最晚的“下工时间”。
- 重叠记工取结束时间最晚的一笔；没有结束时间的进行中记工显示“下工时间 · 未定”。

### 8.5 格子显示内容

至少显示：

- 开始时间。
- 结束时间。
- 项目简称。
- 大费总额。
- 小费总额。
- 大费付款方式。
- 小费付款方式。
- 已确认付款使用金额化摘要：刷卡金额用细线方框包围，现金金额不加框；混合付款按“框内刷卡金额 + 无框现金金额”显示，例如刷卡 $30、现金 $50 显示为 `[30]+50`。礼物卡金额必须带“礼卡”文字标识，不得伪装成现金或刷卡。
- 已确认付款的小费合计为 0 时，卡片付款摘要直接显示数字 `0`，不显示“金额为 0”等额外说明。
- 已确认记录的实际服务付款与应收金额不一致时，卡片右下角显示红色“！”；标记只比较服务付款，不因小费为 0 或小费差异触发。
- 额外项目只在卡片右上角显示绿色小型“＋”标志，不在卡片底部显示“有加项”文字；可与高亮、折扣和待结账标记并排。
- 折扣标记；今日卡片使用 `off5`、`off10` 这样的红色紧凑标签显示折扣总额，不重复显示货币符号或小数位。
- 待结账状态。

主表格只显示大费总额：

`项目金额 + 额外项目金额`

不显示折扣金额。

### 8.6 待结账

初次创建后使用浅橙色背景。

只有付款信息填写完整并通过统一“保存”按钮确认后才解除。

- 同一员工可以同时保留多笔待结账记录；新建第二笔不得因第一笔尚未结账而报错。
- 多笔记工时间重叠时，员工行显示结束时间最晚的一笔作为下工时间。

- 小费输入 0 表示无小费。
- 小费留空表示忘记填写或尚未填写。
- 草稿状态必须保留“留空”和“明确输入 0”的区别。
- 确认付款时，现金、刷卡与礼物卡大费至少有一项被明确填写；未填写的付款方式自动按 0 保存。混合付款可同时填写多种方式。
- 勾选使用礼物卡后必须填写礼物卡序列号，并分别填写礼物卡支付的大费与小费；两者至少一项大于 0。未勾选时序列号保存为空，礼物卡金额保存为 0。
- 现金、刷卡与礼物卡小费都可以留空，确认时自动按 0 保存。
- 免费或免单记录允许三种大费最终均为 0，但用户仍需在至少一个大费字段中明确输入 0。
- 确认后现金、刷卡、礼物卡的六个付款拆分金额都保存为非空金额。
- 记工详情的普通付款输入按支付方式分成两行：第一行为“刷卡：大费、小费”，第二行为“现金：大费、小费”；手机和桌面保持相同顺序，礼物卡继续使用独立区域。
- 详情页只提供一个“保存”按钮。待结账记录的付款信息完全空白时只保存记工修改并继续待结账；只要任何大费、小费或礼物卡字段开始填写，就校验完整性并在保存详情后确认付款。已经确认的记录再次保存时始终重新校验并同步付款。显式填写大费 `0` 视为已开始填写，可用于免费服务；小费留空按 0 处理。
- 实收服务费与折后大费业绩不一致时显示警告，但不阻止确认。

### 8.7 员工右侧统计

同时显示：

- 大费总额。
- 小费总额。
- 应得工资。

### 8.8 礼物卡销售

- 每个营业日在所有员工行下方固定显示独立的“礼物卡销售”栏目；即使当天尚未卖卡也保留新增入口。
- 新卡表单默认显示每家店从 1001 独立递增的下一张号码；用户可直接改为最长 120 字符的自定义序列号。未修改建议号码时由服务端在事务中自动分配，手动修改时提交自定义号码；软删除也不复用旧号。
- 每笔销售记录礼物卡面值、售出时的折扣门槛/比例快照、折扣金额、实际收款、现金付款、刷卡付款和操作人。操作人从本店在职成员列表选择。
- 店铺可设置礼物卡“满指定面值、按百分比折扣”；`面值 - 折扣 = 实际收款 = 现金 + 刷卡 > 0`，由服务端按整数美分最终校验，客户端即时预览。
- 同一店铺的序列号不可重复；序列号比较使用 Unicode 规范化并忽略大小写、重复空白与首尾空白，已软删除的历史号码也不得重新用于新销售。
- 礼物卡销售沿用记工的营业日写入权限、日结锁、幂等、乐观锁、软删除与审计规则。普通员工只能修改当前营业日，店主和经理可修改未日结的历史营业日。
- 卖卡金额全部计入店铺收入，不产生员工工资或分成；卖卡收到的现金也不进入员工现金结算。
- 礼物卡消费只要求记录序列号和本次使用金额，不自动核销余额；同一序列号可跨多笔记工使用，也允许录入上线前已售出的礼物卡。
- 财务页提供礼物卡台账，按序列号自然排序并展示售出日、面值、折扣、实际收款、售出人、付款方式和同卡多条使用记录。

## 11. 金额定义

设：

- P = 主要项目金额。
- E = 额外项目总额。
- D = 折扣总额。
- CS = 现金大费。
- CC = 刷卡大费。
- GCS = 礼物卡大费。
- CT = 现金小费。
- CCT = 刷卡小费。
- GCT = 礼物卡小费。

### 11.1 大费基数

`大费基数 = P + E`

### 11.2 折后大费业绩

`折后大费业绩 = P + E - D`

统一使用“折后大费业绩”这一名称。

### 11.3 实收服务费

`实收服务费 = CS + CC + GCS`

### 11.4 小费总额

`小费总额 = CT + CCT + GCT`

### 11.5 客人总付款

`客人总付款 = CS + CC + GCS + CT + CCT + GCT`

### 11.6 今日流水

`今日流水 = 折后大费业绩 + 礼物卡销售实际收款 - 礼物卡核销支出`

今日流水只显示在财务汇总的每日小计中，不包含小费、员工收入或实际服务付款拆分，由后端按整数美分计算。

### 11.7 不匹配处理

理想情况下：

`CS + CC + GCS = 折后大费业绩`

允许不一致，仅警告，不阻止保存。可能用于欠款、免单、少收、多收、特殊调整等。

第一版金额输入约束：

- 项目、额外项目、折扣、现金大费、刷卡大费、礼物卡大费、现金小费、刷卡小费、礼物卡小费均不得为负数。
- 折扣总额不得超过大费基数；免费服务可令折扣总额等于大费基数。
- 第一版不使用负数模拟退款或冲正；退款属于后续独立流程。
- 因第一版不包含退款专项流程，本节“不匹配”主要用于欠款、免单、少收、多收和特殊调整。

## 12. 工资计算

### 12.1 主要项目工资

`主要项目工资 = 项目金额 × 最终提成比例`

### 12.2 额外项目工资

每个额外项目单独计算：

`额外项目工资 = 额外项目金额 × 该额外项目最终提成比例`

### 12.3 大费工资

`大费工资 = 主要项目工资 + 所有额外项目工资`

### 12.4 员工应得总收入

`员工应得总收入 = 大费工资 + 现金小费 + 刷卡小费 + 礼物卡小费`

折扣不减少工资。

## 13. 每日现金结算

### 13.1 现实现金流

员工每天会拿走当日全部现金，包括：

- 现金大费。
- 现金小费。

每天关门后，通过“结算今日现金”确定员工应保留和应提交的现金。

### 13.2 现金工资分摊

员工保留的现金部分必须按真实提成计算，不使用固定 60%。

若一单含现金大费以及刷卡或礼物卡大费，则将本单大费工资按全部实际服务费中的现金占比分摊：

`本单现金对应大费工资 = 本单大费工资 × 现金大费 / 本单实收服务费`

若实收服务费为 0，系统需安全处理并提示异常。

现金不足以覆盖上述工资时，不能把员工实际没有收到的钱视为已经取得：

`本单实际通过现金取得的大费工资 = min(本单现金大费, 本单现金对应大费工资)`

`本单现金工资缺口 = 本单现金对应大费工资 - 本单实际通过现金取得的大费工资`

若实收服务费为 0，则本单现金对应大费工资和实际通过现金取得的大费工资均为 0；全部大费工资继续计入老板尚欠。

### 13.3 当日公式

`员工共收到现金 = 当日现金大费 + 当日现金小费`

`员工实际通过现金取得的大费工资 = 各单实际通过现金取得的大费工资之和`

`员工应保留现金 = 员工实际通过现金取得的大费工资 + 当日现金小费`

`员工应提交店铺现金 = 当日现金大费 - 员工实际通过现金取得的大费工资`

员工应提交店铺现金不得为负数。现金工资不足部分继续计入老板尚欠，并在现金结算页面提示。

示例：

- 大费基数 100。
- 折扣 10。
- 客人现金支付大费 90。
- 现金小费 20。
- 项目提成 60%。

则：

- 员工大费工资 60。
- 员工应保留 60 + 20 = 80。
- 员工共收到 90 + 20 = 110。
- 员工应提交店铺 110 - 80 = 30。

### 13.4 结算今日现金页面

主要在每日下班结算时出现；拥有者或经理可返回历史日期重新查看。

每位员工显示：

- 今日现金大费。
- 今日现金小费。
- 今日共收到现金。
- 今日现金对应大费工资。
- 今日实际通过现金取得的大费工资。
- 今日现金工资不足金额。
- 今日应保留现金。
- 今日应提交现金。
- 未结清/已全部结清。
- 备注。
- 结算人和时间。

现金结算页面只显示该营业日存在未删除记工记录的员工；完全没有记工的员工不显示，也不进入一键全部结清。

仅两种状态：

- 未结清。
- 已全部结清。

不记录实际提交金额，不做部分结算，不做双方净余额。

支持：

- 单独标记。
- 一键全部结清。
- 取消已结清状态。
- 查看历史。
- 完整操作日志。

## 14. 工资结算与老板尚欠员工

### 14.1 工资结算账本

第一版必须实现，仅限拥有者和经理操作。

字段：

- 员工。
- 结算日期。
- 覆盖开始日期。
- 覆盖结束日期。
- 大费工资金额。
- 现金小费金额。
- 刷卡小费金额。
- 其他调整。
- 本次支付总额。
- 支付方式。
- 备注。
- 操作人。
- 创建、修改、删除与审计信息。

金额关系由后端确定性计算：

`本次支付总额 = 大费工资金额 + 现金小费金额 + 刷卡小费金额 + 其他调整`

- 大费工资金额、现金小费金额和刷卡小费金额必须为 0 或正数。
- 其他调整允许为正数、0 或负数。
- 本次支付总额不接受前端自行计算的最终值。

支持：

- 部分支付。
- 超额支付。
- 负数调整。
- 修改、撤销、删除、恢复。
- 日期范围结算。

### 14.2 尚欠工资

现金结算已结清的营业日中，员工已经通过现金获得：

- 实际通过现金取得的大费工资。
- 全部现金小费。

确定公式：

`老板尚欠员工 = 员工累计应得总收入 - 已通过已结清现金结算实际取得的收入 - 工资结算账本累计已支付`

若结果小于 0，界面不显示负数欠款，而显示“老板尚欠 $0”和“已超额支付 $X”。拥有者本人的服务收入不进入老板尚欠和工资结算。

不得与员工应提交店铺现金合并成“双方净余额”。

员工可查看自己的：

- 累计应得。
- 已通过现金获得。
- 老板已支付。
- 老板尚欠。
- 工资结算明细。

## 16. 日结

- 礼物卡销售张数、现金、刷卡和销售总额。
- 店铺收入（包含礼物卡销售）。

必须重点显示：

- 每人折后大费业绩。
- 每人应得工资。
- 全店折后大费业绩。

日结前检查：

- 待结账记录。
- 小费留空。
- 金额不匹配。
- 异常负数。
- 未填写结束时间。

日结非阻塞提醒：

- 手动改价必须显示提醒并提供对应记工的查看入口，但不阻止普通日结，不禁用“确认日结”按钮，也不单独显示强制日结入口。

允许强制日结。

全店日结页面的每类异常必须提供对应记工的直接查看入口。入口携带店铺、营业日和记工编号，打开今日/历史记工页后自动定位并打开该笔详情，避免只显示异常数量却无法排查。

### 16.1 个人日结

- 今日页面的每个员工行提供“个人日结”入口；拥有者和经理可打开任意员工，普通员工只在自己的员工行看到入口。
- 财务页向员工提供“我的日结”标签，但后端响应只包含本人合计与本人异常，不包含全店合计、其他员工数组或他人的记录编号。
- 个人日结页面和 Mac 代理 PNG 都用二维汇总表整理已确认收入：大费工资和小费工资分别按现金、刷卡和合计展示，今日总收入在同一白色汇总区内独立突出。待结账记工不进入这些已确认收入。
- 现金交接固定显示在逐笔记工之前。个人日结不显示“请先核对”提示区；待结账状态仍在对应逐笔记录上明确标识。
- 个人日结随后按开始时间展示该员工当天每一笔记工，包括主要项目、加项、状态和本单收入。逐笔的“员工大费（折前）”必须使用 `grossFeeBaseCents`，不得使用减去折扣后的实际大费付款；现金、刷卡、礼物卡的大费实收拆分仅作为次级付款信息。代理图片中的现金金额直接显示，刷卡金额使用细线圆角框，礼物卡金额追加括号说明，零金额不占位置。
- 个人日结不显示折扣金额。员工接口只返回目标员工自己的记录，不加载全店或其他员工数据。
- 个人日结的应提交现金独立按 `所有含现金大费的已确认项目折前大费基数之和 × 40%` 计算；不减折扣，不以实际收到的现金大费为基数，也不复用每日现金结算的实际留存公式。
- 现金大费分红为已确认记工按现金付款占现金、刷卡与礼物卡全部服务费的比例分配的工资，非现金大费分红为未通过现金分配的剩余工资（包括刷卡、礼物卡与免费项目仍应获得的工资）。现金小费单独汇总，刷卡与礼物卡小费合并为非现金小费。四项相加等于已确认记工的大费工资与小费合计。
- 个人日结图片按当前设备宽度和像素密度生成；记录较多时自动增长为长图，确保逐笔记工与付款不会被截掉。支持文件分享的手机通过系统分享菜单保存到相册，其他浏览器降级为下载 PNG。

## 19. AI 记工助手

### 19.1 能力

支持中文和英文文字/语音输入。

- 记工助手提供显式语音按钮，每段录制 6–60 秒；转写结果回填输入框，允许用户修改后再发送。
- 语音识别调用 MiniMax `music-cover` 音频预处理接口内置的 ASR，与文字理解共用 MiniMax API key；浏览器或模型不支持时保留文字输入和系统键盘听写。
- 原始录音上限 8 MB，只在请求内存中流转，不持久化。

可理解：

- 员工姓名。
- 项目。
- 时间。
- 金额。
- 额外项目。
- 折扣。
- 混合付款。
- 小费。
- 修改哪一条记录。

### 19.2 工作流

1. 理解自然语言。
2. 生成结构化预览。
3. 展示完整预览。
4. 用户确认。
5. 写入数据库。

AI 不得直接执行任意 SQL。

员工通过 AI 操作其他员工记录时，必须明确姓名并展示完整预览。删除必须二次确认。

## 20. AI 财务助手

- 财务页面提供 AI 聊天入口。
- 第一版接入 MiniMax，但必须通过可替换 Provider 层封装。
- AI 只负责理解和解释，计算必须由后端统计工具完成。
- 员工只能查询自己。
- 经理和拥有者可查询本店授权数据。
- AI 不得跨店。
- 查询保留日志。
- AI 不直接修改财务结算数据。

示例：

- 计算 Amy 最近 7 天刷卡小费。
- 统计本月所有员工折后大费业绩。
- 计算老板尚欠 Amy 多少钱。
- 查看今日未结清现金员工。

## 21. 数据与快照要求

精确表、字段、索引和约束以 `packages/database/prisma/schema.prisma` 与向前迁移为准，产品文档不复制一套易过时的数据库清单。数据模型必须覆盖：

- 用户、店铺、成员关系和加入审批。
- 每日班次、员工行、项目目录和提成规则。
- 记工及主要项目、加项、折扣、付款拆分的历史快照。
- 礼物卡销售和按序列号关联的每次使用记录。
- 日结、现金结算和工资结算的独立状态或账本。
- 审计、幂等请求、实时 outbox 和 AI 预览/查询日志。

每条记工必须保存其营业日、员工、时间、状态、版本、操作人，以及创建当时的项目名称、时长、价格、折扣、提成来源、工资和营业日规则快照。付款确认后分别保存现金、刷卡、礼物卡的大费与小费金额；使用礼物卡时保存序列号。

明细与必要的历史汇总快照可以同时保存，但所有写入汇总都由服务器从明细重算，不信任前端最终合计。数据库约束、事务、乐观锁、幂等、软删除和同事务审计共同保证可追溯性。
