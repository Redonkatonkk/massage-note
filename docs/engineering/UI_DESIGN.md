# UI 设计与审美准则

> 适用版本：`1.18.10` · 设计参考核对：2026-10-02 · 审美准则整理：2026-10-05

本文是后续 AI 修改前端及生成工资结算、个人日结图片时的设计依据。审美判断来自门店工作场景、用户对相邻面板、高亮颜色、成员操作、手机阅读与生成图片的反馈，以及现有实现。用户的新要求优先；具体业务规则以 [产品文档](../product/PRODUCT.md) 为准，具体样式值核对下方源码入口。保留原因：设计依据需要延续，也需要能够随明确反馈修正。

## 审美目标

Massage note 应像一份整理清楚、可以长期使用的门店工作账本：安静、清晰、可信，信息充足，操作直接。店员忙时要快速记工，经理要逐笔核对，店主要看懂金额和支付结果。视觉的价值是让人能很快找到对象、读懂结果、知道下一步，并在长时间使用后仍觉得有秩序。保留原因：这些使用任务共同决定了本项目的视觉气质和信息密度。

整洁感主要来自一致的对齐、稳定的间距、清楚的文字层级和有依据的分组。每一道边线、每一块底色、每一次加粗都应能说明它表达了什么。色彩和装饰的数量保持克制，重点留给记录、金额和正在进行的操作。保留原因：高频工作页的注意力有限，视觉强调必须帮助用户判断。

统一的范围包括首页、全部财务和设置子页面、个人资料、登录、初始化、帮助、离线及弹层，也包括空列表、加载、失败、停用和只读状态，以及 Web 导出的工资结算／个人日结 PNG、短信中的区间结算 JPEG／个人日结 PNG。低频页及生成图片仍须遵循同一套规范。保留原因：用户会通过多个入口完成一件工作，切换页面或查看附件时应能沿用已经学会的阅读方式。

## 如何判断一个设计是否合适

### 同级模块保持同一种视觉语法

相邻且职责相近的模块共用表面、边框、圆角、标题层级和操作样式。今日空表、员工操作、礼物卡销售、跑客记录的面板外观保持一致，内容多少通过自然高度和内部排版表达。空状态也沿用原有面板，不因“没有数据”新增虚线框、胶囊形状或另一种底色。保留原因：同级对象的外观一致，用户才能把差异理解为数据差异。

布局可以根据任务不同而变化。目录适合选择对象，表格适合比较多行，带标签的记录适合逐条核对，表单适合编辑。先复用已有结构，再判断是否需要增加容器；一组连续字段通常用标题、间距和细线分组即可。保留原因：共同的视觉语言需要保留任务差异，反复嵌套面板会增加噪声和缩窄内容。

### 信息顺序决定阅读顺序

每页先给出当前店铺、日期或范围，再给出页面任务与关键结果，随后展示对象和明细，操作放在与其对象紧邻的位置。姓名、金额、状态和原因之间要有明确对应，次要说明用较轻的文字层级。保留原因：人会先确定自己正在看什么，再判断结果，最后决定操作。

一段操作流程中的主要动作突出一次；辅助动作使用较轻的样式，删除、解除和转移与日常操作保持清楚的距离。错误、预算性质、未结账、删除原因和历史修改提示应出现在作出决定之前，完整 JSON、尝试次数等技术或次要信息按需展开。保留原因：视觉层级应对应动作的重要性和作出决定所需的信息。

成员管理坚持先选择已有员工，再集中查看和修改该员工的详细资料。手机详情保留返回名册入口，资料、工资和账号状态分组组织。保留原因：一次围绕一个明确对象编辑，能减少查找负担和误改，操作结构本身也是整洁感的一部分。

### 密度由内容关系决定

属于同一个对象的标签、值、状态和操作靠近排列；不同任务之间留出较大的间距。标题、正文、表单和金额按共同基线对齐，字段帮助文字留在自己的字段内，不拉高相邻控件。保留原因：距离和对齐表达信息关系，用户无需逐句阅读也能理解分组。

首页保留充足的记工空间，桌面侧栏继续默认收起，悬停或键盘进入时展开并覆盖内容。手机允许内容自然向下增长，字段和操作自然换行。内容变长时优先调整列数、分组和展开层级，避免靠缩小字号、裁切关键值或固定高度塞下所有内容。保留原因：空间分配要服务实际工作量，真实数据长度不能破坏阅读。

### 颜色表达确定的含义

石灰白页面、白色工作表面和墨色正文形成底层秩序，深绿色用于主操作和选中语义。高亮记工使用柔和灰绿色，并在记工卡、编辑和财务明细中延续；浅橙待付款、绿色成功、红色错误或危险操作各有明确用途，并配合文字。图表比较序列沿用已有语义变量。保留原因：同一种颜色持续表达同一种含义，用户才能形成稳定预期。

高亮应让记录容易找到，同时保持正文和金额清楚可读；悬停、按下和只读时保留高亮含义。新增页面使用既有颜色变量，新增语义颜色时先说明需要表达的状态，再在共享入口定义。避免为某个模块单独指定一套品牌色。保留原因：局部强调不能改变整个页面的视觉重心，也不能形成新的调色板。

### 文字与金额承担主要表达

沿用系统字体、共同字号和线性图标体系。标题交代任务，标签说明字段，说明文字尽量写清可执行的动作。中文、英文、长姓名、手机号、序列号和连续身份 ID 都纳入内容长度判断；关键对象、金额、删除原因和错误应完整可查。保留原因：界面主要靠文字完成记工和对账，真实文案比理想长度更能检验布局。

金额使用共同格式化入口和等宽数字，同类金额保持一致的对齐与标签；工资结算保留美分。零值、空值、预算与实付需要明确区分，不能为了简洁删掉单位、来源或混合付款提示。最终财务口径和分摊继续来自原有服务端与领域规则。保留原因：金额看起来整齐的同时必须能被正确解释和核对。

生成图片先交代店铺、日期／范围和员工，再突出一个主要收入结果，随后按大费和小费核对来源，最后查看时间顺序明细。个人日结的来源按现金、非现金（刷卡＋礼卡）、合计纵向排列，标签和值紧邻；逐笔分开说明员工收入、折前金额与客人付款来源。待结账写明未计入汇总，未知显示“未确认”，零金额保留数值；收入资料不能暗示已经支付工资。保留原因：图片通常在手机消息中阅读，清楚的顺序和字段名比颜色或边框更能帮助人理解金额。

## 手机布局的判断方法

手机上的任务顺序与桌面保持一致，具体排列按可用宽度调整。逐条核对的账本、回收站、发送队列和支出明细使用带字段名的纵向记录：对象和日期在前，关键金额及状态随后，原因和错误可直接读取，次要明细按需展开，最后是本条操作。保留原因：窄屏需要让标签和值保持相邻，减少来回横滑寻找对应字段。

每周排工、跨日比较和图表可以保留矩阵及独立横向滚动，并提供必要的固定行列标识或说明。所有滚动限制在对应容器内，页面本身保持正常宽度。长编辑弹层保持关闭入口可达，内容独立滚动；输入字号和触控区域遵循公共基线。保留原因：这些结构需要表达行列关系，明确上下文和足够的操作区域才能支持手机阅读。

不能用“媒体查询存在”或“颜色变量一致”推断手机已经易读。逐页核对对象、字段名、值、状态、提示和操作在 DOM 中的排列，并覆盖长文案、多个金额来源、空列表及失败状态。保留原因：响应式样式和阅读结构是两个需要分别检查的层面。

## 本项目已经暴露过的问题

| 问题 | 设计判断 | 后续维护方式 |
| --- | --- | --- |
| 相邻小面板各自使用不同圆角、底色、虚线与形状 | 同级模块缺少稳定的外观关系。 | 复用 `.board-panel`，只根据内容调整内部布局；空状态延续同一表面。 |
| 高亮记工颜色过亮，压过正文与金额 | 强调幅度超过这条记录的任务权重。 | 复用灰绿色高亮变量，所有展示与交互状态持续表达同一含义。 |
| 手机保留 8–21 列记录表 | 姓名、金额、原因与操作无法同时对应。 | 逐条记录改用公共手机展示；真正需要跨行列比较的矩阵保留受控滚动。 |
| 工资汇总四列挤成约 11px 字号 | 关键金额需要优先保证可读性。 | 按大费和小费分组，标注来源与合计，保留美分。 |
| 工资结算图片使用暖色渐变、红棕大底色、阴影和过重字重 | 导出资料脱离了页面的共同视觉语言，装饰压过金额与明细。 | Web 与短信共用共享 SVG，沿用石灰白、白色、墨色与深绿，使用细边线、统一圆角和来源标签；长内容完整换行。 |
| 个人日结图片左右挤压项目与多个金额，付款方式只靠数字外框区分 | 读者无法顺着同一个方向把员工收入、客人付款和来源对应起来。 | 先显示已确认总收入，大费／小费按来源纵排，逐笔使用明确字段名与付款来源，未知和待结账用文字说明。 |
| 短信号码与图片语言被帮助文案拉成不同高度 | 文案和控件关系破坏了字段基线。 | 标签、控件、帮助分别布局；手机按自然顺序堆叠。 |
| 机器人身份、访问权限、工作状态与解除挤在一行 | 一个成员包含不同性质的信息和动作。 | 身份及状态在前，操作独立成行；长身份完整换行。 |
| 审计展开后先看到大块 JSON | 常规核对需要能直接理解变化。 | 先显示已知字段的标签、值与修改前后，再展开完整原始数据。 |
| 帮助主题只跳到尚未展开的内容 | 导航没有完成用户想要的阅读动作。 | 点击主题同时展开并聚焦对应说明，保持原生链接和折叠语义。 |

这些例子用于学习判断方法，避免只修某张截图里的一个控件。修复共享样式时要检查相邻模块、其他分区、数据状态和手机断点。保留原因：局部症状可能来自公共组件或后加载的覆盖规则。

## 后续 AI 的工作顺序

1. 读本页、相关产品规则和现有组件，先写清页面服务谁、当前对象是什么、下一步是什么。保留原因：任务含糊时容易用装饰代替布局判断。
2. 根据任务选择现有目录、表格、纵向记录或表单结构，再确定内容顺序和主次操作。保留原因：布局应先有信息依据，样式随后表达层级。
3. 复用共享组件、颜色、圆角、控件和图标，检查实际 CSS 加载顺序与后续断点覆盖。保留原因：局部相似仍可能在其他状态下产生不同外观。
4. 检查桌面、手机、低频子页面和弹层，以及长姓名/英文、关键金额、加载、空状态和错误。保留原因：完整内容与状态决定设计能否持续使用。
5. 按 [开发指南](DEVELOPMENT.md) 做与改动相称的验证，在交接中说明验证范围。默认只做代码、命令行/API 检查；用户明确要求时才用浏览器。保留原因：延续用户的验证偏好，同时避免把自动化检查通过写成视觉或真机验收完成。

完成前应能解释：每个强调元素表达什么，同级元素为何一致，用户如何把金额对应到对象，手机上的下一步是否清楚，低频页是否沿用共同规范。解释不清时先修改结构或减少无依据的强调。保留原因：这些问题能把审美要求转为可复核的设计选择。

## 方向与来源

界面围绕门店的高频记工、对账和人员维护组织。石灰白背景、白色工作表面、墨色正文与深绿色主操作组成基本层次；边线和留白承担分组，弹层才使用阴影。去掉装饰渐变、卡片浮起和大面积品牌色。灰绿色高亮、浅橙待付款、绿色成功与红色错误仍各有明确含义，不仅依靠颜色辨别状态。保留原因：表面层级用于高频工作，状态颜色各有含义并需文字辅助。

现有设计来源如下；仅借鉴布局原则，成员工具栏的代码改写另有许可证声明。

- [Radix 字号体系](https://github.com/radix-ui/themes/blob/1faff10ac26ae17f09944d418c6949b93fc6b566/packages/radix-ui-themes/src/styles/tokens/typography.css) 与 [间距体系](https://github.com/radix-ui/themes/blob/1faff10ac26ae17f09944d418c6949b93fc6b566/packages/radix-ui-themes/src/styles/tokens/space.css)：统一字号层级，按 4/8/12/16/24/32px 组织间距。
- [Cal 设置页头](https://github.com/calcom/cal.diy/blob/54343aa685ae8f33159d2f485ec4a57bad5c574a/packages/features/settings/appDir/SettingsHeader.tsx)：标题、用途说明与主要操作形成稳定页头，分界使用细边线。
- [Twenty 成员设置](https://github.com/twentyhq/twenty/blob/2fedea0fa394c9f4997ca46d157956f4e562a748/packages/twenty-front/src/pages/settings/members/SettingsWorkspaceMembers.tsx)：成员、邀请与权限具有不同任务边界，避免同时堆叠全部操作。
- 原有成员搜索工具栏对 shadcn/ui 的改写继续保留，其许可证见 [第三方声明](THIRD_PARTY_NOTICES.md)。保留原因：MIT 要求在分发的改写代码中保留版权与许可证。

基础字号为 16px，正文通常 14–16px，辅助文字 12–14px，页面标题约 28px，金额使用等宽数字。按钮与输入框圆角 6px，主要工作面板 10px；高频主操作触控高度至少 44px。字体采用本地系统字体，不依赖第三方字体请求。保留原因：这是当前样式变量与触控基线，旧十九像素及大圆角规则已无对应实现。

## 样式维护规则

- 颜色变量与基础规则在 `globals.css`，共享视觉/动效在 `design-system.css`，媒体断点在 `responsive.css`，按此顺序加载。保留原因：实际层叠依赖顺序，跨文件再次写独立表面会覆盖共享设计。
- 记工空表、员工操作、卖卡与跑客共用 `.board-panel`；断点只调布局，手机卖卡/跑客单列。保留原因：这些模块使用相同工作表面，旧“始终左右并排”不符合当前断点。
- 原生文本、日期、月份和下拉框使用公共基线，fieldset 标题/内容分别布局，字段顶端对齐。保留原因：原生语义和禁用传播必须保留，辅助说明不能拉伸相邻控件。
- 颜色、圆角使用共享变量，修改样式运行 `pnpm ui:check` 和 `pnpm ui:mobile`。保留原因：前者检查变量来源，后者按实际加载顺序核对手机断点的表面、字段、触控高度与布局，并覆盖卖卡/跑客四种数据组合；退化样例验证检查器能发现覆盖问题。
- 工资结算与个人日结图片各由共享 SVG 统一 Web 导出和短信附件，共用主题、文字换行与表面绘制：石灰白背景、白色表面、墨色正文、深绿重点、细边线和统一圆角，不使用装饰渐变、阴影、红棕大底色或过重字重。按“对象与日期 → 主要收入 → 来源汇总 → 逐笔明细”组织，主要收入只突出一次；大费、小费、员工收入与客人付款分别标注，金额保留美分。店名、姓名、项目、付款拆分和长金额完整换行，图片随内容增高。保留原因：附件也是同一份工作账本，颜色、阅读层级和字段对应需要同时延续页面语义，完整金额与对象才能用于核对。

## 导航与页头

1200px 起默认使用 64px 的图标侧栏，鼠标移入或键盘焦点进入时展开至 216px，显示名称、当前财务或设置分区的子页面及语言切换。鼠标移开且没有键盘焦点时自动收回；鼠标点击留下的普通焦点不会阻止收回。展开覆盖内容，不改变主区域宽度或引发横向跳动；主区域只预留 64px，并取消桌面的 1600px 最大宽度限制。收起入口保留可访问名称，隐藏的子菜单和语言按钮不进入 Tab 顺序。小屏继续使用同一组入口的底部导航与横向页面标签。角色权限、店铺参数与 URL 分区恢复由原有导航辅助函数决定。保留原因：收起和展开共用导航状态，覆盖式展开避免记工主区域跳动。

财务和设置的页头直接显示当前子页面的标题及任务说明；桌面子菜单与小屏标签共用选中状态。语言切换在桌面侧栏底部，小屏在全局工具区；登录和初始化页继续保留语言入口。AI 助手沿用记工与财务导航入口及 body portal，弹层位于侧栏右侧，软键盘与焦点回退逻辑保留。保留原因：同一路由和角色菜单避免桌面、小屏及语言入口各维护一套行为。

## 交互边界与验证

- 临时反馈继续由共享计时器在 3 秒后清理；同步、离线、锁定、预算等持续状态由真实业务状态决定。保留原因：短期操作反馈由计时器管理，持续业务状态不能按时间消失。
- 高亮记工的底色与边框持续存在，悬停、按下及只读均不改变；待付款保留单独状态文字。保留原因：高亮也是业务标记，悬停不能使其变成普通记录。
- 记工编辑、快速录入与发送队列保留 portal、固定顶部关闭入口、表单滚动和设备安全区。保留原因：长表单与软键盘需要独立滚动和安全区，背景不能漂移。
- 月度日历缓存、自动同步刷新范围、金额口径、角色权限、营业日锁与历史快照均保持原有规则。前端不重新计算财务。保留原因：这些规则已在产品文档定义，视觉修改不能引入第二套财务计算。
- 结算及个人日结图片变更检查共享 SVG 的阅读顺序、字段名、配色、字重、完整文字和来源金额，并运行领域、Web 图片与 Mac 代理渲染回归。个人日结保留已确认汇总、待结账提示、未知／零值区分和固定源宽；区间结算保留每天总结最左、逐笔时间顺序、2～4 列及长图容量边界。保留原因：网页 CSS 检查不覆盖生成图片，同一模板在不同输出环境中都须保持完整账目和金额语义。
- `pnpm ui:mobile` 使用实际三份 CSS 和代表性 DOM 结构，在 320、360、390、414、480、600、760px 核对全部 8 个路由、27 组页面/分区与常用弹层；新路由缺少样例时检查失败。手机支付字段与单一来源金额预览按列堆叠，输入字号至少 16px；大表和图表仅在各自容器横向滚动。成员流程另用 React + jsdom 覆盖长姓名、空列表、停用、冲突及展开状态。保留原因：样式覆盖与业务交互需要分别检查。上述代码检查不启动浏览器，不计算真实布局、文字截断、软键盘或容器查询的实际尺寸，不能证明最终视觉效果；视觉评价由用户进行。
