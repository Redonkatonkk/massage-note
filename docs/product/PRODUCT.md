- 第 6–10 节：营业日、项目配置、今日记工与详情编辑。

本文整理 Massage note 的产品范围、角色权限、记工与财务口径。它说明“系统应该做什么”；接口字段、代码位置和部署步骤分别由 API、架构和部署文档负责。

## 1. 产品目标

开发一套多店铺使用的按摩店记工与财务管理系统，替代纸质手写记工表。主要使用设备为手机，同时支持 iPad 与电脑。系统必须简单、清晰、适合年龄较大的员工使用，并保证财务计算准确、历史数据可追溯、多设备实时同步。

## 2. 核心原则

1. 旧记录像写在纸上一样永久保留当时内容，不因后续项目、价格、提成比例或折扣模板修改而变化。
2. 所有金额使用整数美分存储，避免浮点误差；所有页面、AI 答复和个人日结图片中的只读金额统一四舍五入显示为整美元，不显示小数点，且不得改变底层账本值。金额编辑框不再自动补 `.00`，遇到既有真实美分时仍保留其精确值，避免编辑即改账。
3. 所有关键修改保留审计历史。
4. 所有删除使用软删除。
5. 折扣由店铺承担，不减少员工工资。
6. 现金大费、刷卡大费、现金小费、刷卡小费必须分别保存具体金额。
7. 财务由后端确定性计算，AI 只负责理解自然语言和调用受限工具。
8. 系统支持多店铺、多角色、多设备同时登录与实时同步。
9. 第一版以响应式 Web 应用为主，不提供浏览器安装入口；后端 API 与业务逻辑必须可复用于未来 iPhone/iPad 应用。
10. 界面支持简体中文和英文；没有本机语言偏好时默认使用简体中文，用户可在登录、断网、帮助和全部业务页面随时切换，选择在本机持久保留。英语界面对店铺自定义的中文主要项目、加项和折扣名称自动显示领域英译，但编辑时保留原始中文，不得因切换语言改写历史快照。

## 3. 用户与角色

### 3.1 角色

- Owner：拥有者，每家店唯一。
- Manager：经理，与拥有者基本同权，但不能修改拥有者、转移拥有者身份或删除店铺。
- Employee：员工。

角色按店铺维度保存。同一用户可以在不同店铺中拥有不同角色。

权限角色与是否参与记工相互独立：

- Owner、Manager、Employee 均可设置为“参与记工”或“不参与记工”。
- 参与记工的拥有者和经理与普通员工一样出现在今日表格中，并拥有自己的项目提成、记工、小费和财务统计。
- 参与记工的经理按普通员工方式进入工资结算和“老板尚欠员工”计算。
- 参与记工的拥有者仍计算项目工资和小费，供经营核算使用，但不进入“老板尚欠员工”或给自己的工资结算；界面单独显示为“拥有者本人服务收入”。

### 3.2 拥有者权限

- 管理所有记工与历史记录。
- 管理员工、经理、加入申请。
- 只填写名字即可预先创建尚未注册账号的新员工。
- 管理项目、额外项目、折扣项目、提成规则。
- 查看全部财务。
- 进行日结、取消日结、现金结算、工资结算。
- 修改店铺设置。
- 删除店铺。
- 转移拥有者身份。

转移店主的目标成员必须已关联可用登录账号，未认领或被停用的账号不能接管店铺。

### 3.3 经理权限

与拥有者几乎同权，但不能：

- 修改、移除或降级拥有者。
- 转移拥有者身份。
- 删除店铺。

经理可以指定其他经理。

经理也可以只填写名字预先创建新员工。

### 3.4 员工权限

员工可以：

- 查看当天所有员工的记工。
- 为自己或其他员工新增、修改、删除当天记工。删除记工只需确认删除，不再弹出理由输入框；记录仍可由店主或经理恢复。
- 查看所有当天记录详情和公开备注。
- 在今日页面通过营业日日历查看自己任意过去营业日的记工；历史响应只包含本人行、班次、记工和本人小计。
- 使用记工 AI 助手。
- 查看自己的全部历史财务。
- 查看自己的工资结算记录和老板尚欠金额。
- 查看自己的现金结算状态。
- 从今日员工行或财务页查看自己的个人日结，并生成按内容高度排版的 PNG 图片。

员工不能：

- 修改过去营业日记录。
- 查看其他员工历史财务。
- 管理店铺设置、项目、成员、结算与全店日结。
- 查看其他员工或全店日结信息。

## 4. 登录与账号

### 4.1 登录方式

- 使用 Firebase Authentication 手机号验证码登录。
- 仅支持美国手机号。
- UI 输入 10 位美国号码，内部标准化为 E.164，例如 +14701234567。
- 支持同账号多设备同时登录。
- 默认长期保持登录状态。
- 支持退出当前设备和撤销所有设备会话。
- 暂不支持更换手机号和账号恢复。

### 4.2 短信防刷

- 仅允许 +1 国家码。
- 重发验证码倒计时。
- 同号码、同 IP 频率限制。
- 连续错误临时锁定。
- Firebase reCAPTCHA。
- 不泄露号码是否已注册。
- 开发环境使用测试号码。

### 4.3 首次注册

所有用户填写：

- First Name
- Last Name

通常仅显示 First Name 或店铺内 Display Name。

## 5. 多店铺与加入流程

### 5.1 创建店铺

拥有者首次创建店铺时填写：

- 店铺名称。
- 六位数字店铺 ID。

店铺 ID 由拥有者自己输入，必须全局唯一，被占用时要求重新输入。

创建后直接进入店铺设置向导，而不是空白主页。

### 5.2 店铺设置向导

1. 店铺名称。
2. 六位店铺 ID。
3. 店铺时区：默认提取拥有者设备时区，可修改。
4. 营业日：按设备本地日期计算，午夜换日，无需设置关门时间。
5. 店铺全局默认提成比例。
6. 主要项目。
7. 额外项目。
8. 折扣项目。
9. 确认并进入今日主页。

店铺设置页还提供“周一至周四自动折扣”：Owner 或 Manager 可开启规则，设置折前大费应用门槛和固定折扣额度。系统按营业日判断星期，在主要项目与额外项目之和达到门槛时自动添加一项折扣快照。自动折扣可与其他折扣同时存在，由店铺承担，不降低员工大费工资；配置变化不批量改写历史记工。用户可在记工详情中只为当前记录直接移除自动折扣，无需二次确认；该选择会持久保留并可恢复，不会关闭全店规则。

### 5.3 加入店铺

员工输入六位店铺 ID 后：

1. 显示店铺名称。
2. 员工确认。
3. 如果账号注册时填写的 First Name 与本店一个待认领员工的名字相同，系统直接把账号绑定到原成员关系；原成员 ID、记工、提成和财务历史全部保留。
4. 没有匹配项时提交加入申请。
5. 拥有者或经理审批。

### 5.4 显示名与同名限制

- 当前在职成员的店内显示名不得重复，不区分大小写。
- 内部始终使用唯一用户 ID。
- 拥有者可修改员工显示名。
- 已离职员工保留历史名称和记录。
- 拥有者或经理预先创建员工时只填写名字，不要求姓氏或手机号；该成员在账号认领前也可参与记工和配置提成。
- 自动认领只使用账号注册资料里的 First Name 与本店待认领员工名字进行规范化精确匹配，不能靠在加入表单中输入他人的名字冒领。

### 5.5 离职与重新加入

移除员工时：

- 保留全部历史记工、财务和审计。
- 仅停用当前成员关系。
- 重新加入时恢复关联。

## 6. 店铺与营业日

记工页在汇总卡片上方合并营业日选择与操作栏：刷新、日结（已日结时为现金结算）及更多操作在宽屏位于营业日右侧，窄屏在同一区域内换行。按钮按原有角色权限显示。

### 6.1 营业日日期

今日按操作设备的本地日期计算，在当地午夜换日；关门时间或旧营业日截止设置不再影响归属。新记工按开始时间在设备时区下的自然日期归属，跨午夜结束不改变归属。页面打开跨午夜后自动刷新今日日期。

浏览器请求附带设备当前时间和 IANA 时区，服务端在同一请求内统一用于今日、权限与新记工日期计算。无设备信息的机器人或后台请求使用店铺时区的自然日期。已有记录保留保存的营业日；仅修改金额等信息不会重新归日，明确修改开始时间才按新规则计算。旧截止字段只为接口和历史快照兼容保留，不参与计算。

### 6.2 历史日期

拥有者和经理可通过日历切换任意营业日，查看并修改当日主表格。员工也可在今日页面切换过去营业日，但只读取自己的行、班次、记工和本人小计，不能修改历史；员工财务页面同样只显示本人历史。

今日记工和财务“日结”使用同一营业日日历。日历以橙色圆点标记“有有效记工但尚未日结”的日期，并在底部显示说明；已日结日期在日号下以小字显示折后营业额，只显示美元数值（整额无小数，有美分保留两位），不加币种或文字。店主/经理显示全店未删除记工的折后项目金额加未删除卖卡实际收款，不含小费；员工仅显示本人有记工的已日结日期及本人折后金额，不暴露全店或他人财务。取消日结后重新打开日历恢复未日结圆点，不显示金额；已经日结、没有记工、已删除记工和未来营业日不标记。Owner/Manager 看到全店待日结日期，员工仅看到自己有记工的待日结日期，不能借此读取其他员工信息。

已日结营业日的修改规则：

- 日结后员工不能再修改当日记工。记工详情中的保存和删除按钮禁用并呈灰色；店主/经理可在保存左侧点击“取消日结”，成功刷新后恢复保存并保留当前填写内容，员工不显示取消入口。
- 拥有者或经理必须先取消日结，才能修改当日记工。
- 如果该营业日的现金结算已经结清，取消日结或修改记录时，相关现金结算自动恢复为“未结清”，并要求重新确认。
- 已存在的工资结算账本不自动删除；系统根据修改后的记工重新计算尚欠金额，并明确提示“结算后历史数据发生过修改”。
- 修改、取消日结、现金结算状态回退及重新结算均写入审计日志。

## 7. 项目配置

主要项目、额外项目和折扣项目在管理页分为三个独立区域，不使用跨类型的顶部集成表单。各项默认显示名称、价格、时长、默认提成和启用状态摘要，点击“修改”才展开带标签的编辑栏；每类新增表单也默认收起并由分类标题处单独打开。额外项目的名称、简称、金额、时间、默认提成、启用状态和保存操作在桌面宽度下保持一条紧凑横栏，窄屏再按断点换行。三类项目均可独立上移、下移，保存后的顺序用于项目管理、快速记工和详情选择。

### 7.1 主要项目字段

- 完整名称。
- 主表格简称。
- 一个或多个“时长 + 价格”档位；同一项目内时长不能重复。
- 默认提成比例，可为空。
- 排序。
- 启用状态。

例如一个 `Body Massage` 项目可以同时设置：

- 30 分钟 / $60
- 60 分钟 / $100
- 90 分钟 / $150

价格由店铺按项目和时长分别设置，无需为每个时长重复创建项目。项目默认提成、员工项目专属提成、排序和启用状态属于项目本身，所有时长档位共享。

### 7.2 额外项目

字段：

- 名称。
- 简称。
- 默认金额。
- 默认时长，可为空。
- 默认提成比例，可为空。
- 排序。
- 启用状态。

一条记工可选择多个额外项目，员工可修改本次金额、加时分钟或添加自定义额外项目。记工详情始终显示每项“加时分钟”：留空或填 `0` 表示不增加时长；填写 `1–720` 分钟会立即按主要项目加全部额外项目的总时长重算结束时间。预设额外项目会带入其配置分钟数，但本单可按实际服务调整，保存为历史快照。

### 7.3 折扣项目

- 预设折扣目录仍使用固定金额；记工详情的折扣输入支持金额或百分比（例如 `10%`，也接受全角 `％`）。无百分号时按美元金额处理，比例范围为 0–100%，最多两位小数。
- 百分比折扣按主要项目与全部加项的折前金额之和计算，不含小费，四舍五入到美分。多项比例分别按同一折前合计计算，再与固定及自动折扣相加；总折扣不得超过折前大费。
- 保存每项比例与算出的减免金额快照；再次编辑项目或加项金额时自动重算比例折扣，已日结历史不变。右上角 `off` 标记继续显示合计减免美元金额（沿用整美元显示规则），不显示百分比。
- 一条记录可使用多个折扣。
- 员工可使用预设折扣，也可自定义名称和金额。
- 用户输入正数，内部按减免处理。
- 折扣不需要审批。
- 折扣由店铺承担，不减少员工工资。
- 周一至周四自动折扣与普通折扣使用同一折扣总额规则，但由系统根据店铺门槛自动生成和重新判断；记工详情可为单笔记录持久移除或恢复自动折扣。
- 支持独立排序和启用状态。

### 7.4 提成优先级

1. 某员工对某项目的特殊比例。
2. 该员工默认比例。
3. 该项目自身默认比例。
4. 店铺全局默认比例。

每条记录保存最终生效比例快照。
保存员工默认或员工项目专属提成时，系统会按最新完整优先级重算该员工未日结的当前营业日记工，并同步刷新今日小结、个人日结及相关现金工资字段；若现金已经结清则自动回退为待结清。已日结营业日和更早历史记录不得改写。

自定义主要项目和自定义额外项目没有项目默认比例，按以下顺序取值：

1. 该员工默认比例。
2. 店铺全局默认比例。

员工不能在记工时自行修改提成比例。拥有者或经理可以修改本单最终比例，但必须保存修改前后数据和审计记录。

## 8. 今日主页面

- 记工卡片时间采用 `h:mm AM/PM`。快速新增与详情的开始时间、结束时间均使用小时（1–12）、分钟（00–59）输入框和 AM/PM 选择框，中英文界面均直接显示 AM、PM，无需手填时段。详情日期独立选择；结束时间默认按开始时间加主要项目和额外项目总时长计算，修改结束时间则按总时长反算开始时间。已有时间按真实 AM/PM 回填。开始/结束时间及项目时长联动只调整时钟，服务日期只允许通过日期选择器显式修改；跨午夜后结束早于开始时须纠正后再保存，含付款的保存同样校验。记工详情操作报错浮在窗口顶部，显示一秒后淡出消失；时区和营业日归属规则保持不变。

- 营业日日历选择日期后立即加载目标日期，不保留额外“查看”按钮。
- 全店“营业额（折扣后）、折扣总额、礼物卡总额、店铺收入、总收入”汇总只向拥有者和经理展示，普通员工不显示该区域；顶部今日汇总不单独显示小费总额，但店铺收入公式仍包含小费。
- 所选营业日已日结时，顶部显示“过去N天平均营业额”。统计窗口固定为所选当日加之前29个自然日；仅纳入窗口内当前已日结的日期，所选当日金额与天数只计一次。平均值 = 这些日期的全店未删除记工折后业绩与卖卡实际收款合计 ÷ 实际已日结天数N。未日结或缺少日结数据的日期不计入分子和分母；已日结但无服务业绩且无卖卡的日期按零计入。数据库不足30天日结数据时按实际天数计算，不向窗口外补足；只有当日日结时N为1。金额包含卖卡实际收款、不含小费，四舍五入至美分。所选当日未日结或取消日结后不显示；员工不获取该全店指标。
- 顶部营业额（折扣后）使用折后项目业绩加当日未删除卖卡实际收款，不扣礼物卡核销，不影响员工提成基数；礼物卡总额使用当日卖卡实际收款。顶部 `总收入 = 店铺收入 + 店长收入 + 所有经理收入`，店长和经理收入包含大费工资与小费，沿用看板口径（待结账包含已知工资与已知小费）。按所选营业日全部未删除记工计算，隐藏员工行不影响总额；不重复加礼物卡收入，不扣刷卡手续费，与下述财务总结算口径区分。
- `店铺收入 = 营业额（已含卖卡实收）+ 小费总额 - 员工总收入 - 礼物卡核销支出`，其中 `礼物卡核销支出 = 礼物卡大费 + 礼物卡小费`，由后端按整数美分计算。卖卡实际收款全部算店铺收入，不进入任何员工提成、工资或现金结算；客人使用礼物卡付款全部算店铺支出。

- 财务汇总的付款方式默认选择全部。店铺级汇总和日结合计中的全部项目数量等于记工数量加礼物卡销售张数，客人总付款等于记工实收服务费、小费与礼物卡销售实际收款之和。每日小计不显示全部项目数、记工数、实收服务费、小费或客人总付款，日期、星期之后的第一项金额固定为 `今日流水 = 折后大费业绩 + 礼物卡销售实际收款 - 礼物卡核销支出`。员工小计不分摊礼物卡销售；每人直接显示当前默认提成，存在不同项目专属提成时额外标注，不以筛选后的工资反推比例。明确限定员工、仅大费、仅小费或仅高亮记工时，也不纳入店铺级卖卡记录。
礼物卡对记工页总收入、财务每日小计及财务总结算均只影响一次：卖卡按实际收款增加，用卡按大费与小费合计减少；这些收支已包含在店铺收入中，礼物卡净收入字段只用于展示组成，不再次加减。财务总结算继续扣除信用卡手续费；记工页及每日小计保留手续费前口径。

- 财务汇总的店铺总结算显示信用卡手续费：未高亮记工的刷卡大费与刷卡小费按当前筛选范围合计后收取 `2.5%`，含任意所选刷卡金额的高亮记工每笔固定收取 `$3.00`，部分刷卡也按一笔；礼物卡付款、卖卡刷卡和高亮但无刷卡金额的记工不收费。`总收入 = 店铺收入 + 店长总收入 + 经理总收入 - 信用卡手续费`。

### 8.1 桌面与 iPad 横屏

- 每行一名员工。
- 每个格子一条记工。
- 员工姓名、员工操作、记工数图标和个人日结在宽屏共用一行；空间不足时自动换行，手机保留独立操作行，长姓名允许折行。
- 记工数按所选营业日当前未删除的记工条数统计，包含待结账记录，不把加项或礼物卡销售另算一工；折叠员工卡片后仍显示。
- 中间横向显示记录。
- 右侧显示当日统计。
- 大费、小费和应得使用独立标签与金额行，长金额不得粘连、裁切或被悬浮按钮遮挡。
- 行末提供空白“+”格子。
- 支持横向滚动。
- 员工操作仅提供上移、下移调整顺序，不支持拖动排序。员工姓名下方显示工作状态，不再显示全职、兼职或未设置排工类型；姓名前不显示数字名次，仍按排位顺序排列。

### 8.2 手机竖屏

- 每名员工使用折叠卡片。宽度大于 760px 时，展开卡片的姓名、状态、员工操作、记工数和个人日结集中在 168px 左侧栏，位于第一笔记工左侧；右侧大费、小费、应得使用 156px 紧凑金额栏。收起后保留横向员工摘要；手机继续上下排列，记工列表只在自身区域横向滚动。
- 记工卡片在员工区域内紧凑横向排列，可左右滑动查看全部记录。桌面鼠标移到记工卡区域最右侧时显示“跳到最后”按钮，点击滚动到最右端；无溢出或已到末尾时隐藏，手机不显示。键盘聚焦按钮时也会显示。
- 新增记工入口跟随在横向卡片队列末尾。未日结时，展开列表默认显示最右侧，并跟随新增记录；允许手动滑到前面的记工，停止滚动或操作约 10 秒后自动回到最右侧，继续操作会重新计时，按住拖动期间不回位。已日结时不自动回位。自动回位遵循系统减少动态效果偏好。
- 不强行压缩桌面表格。
- 页面和弹窗不得产生横向漂移；页面根节点覆盖动态视口高度并限制下拉边界，不能在底部露出大块空白区域。

### 8.3 员工进入今日表格

- 拥有者或经理可在记工日历选择未来日期（含后续月份），进入对应营业日并提前添加员工；页面数据刷新后保留所选日期。普通员工仍仅可选择今天及过去日期，财务日结和现金结算仍不允许未来日期。
- 拥有者或经理可手动添加员工。当所选营业日没有可见上班员工时，点击“请选择员工”或“添加员工”打开多选弹窗，勾选后点击“添加所选员工”一次提交；员工按勾选顺序逐个加入，选择序号实时显示，取消后重选排到最后。已有可见员工时沿用单人添加。
- 多选保存期间禁止重复提交；中途失败则停止后续添加，刷新已成功加入的员工，弹窗保留尚未完成的选择和错误提示以便重试。取消弹窗不会添加员工。
- 在成员管理中填写名字及全职/兼职即可创建员工；未注册员工会标记为“等待注册”。
- 店主可在成员管理修改自己的店内显示名与默认提成；角色仍须通过店主转移流程变更。
- 成员管理和财务短信接收号码显示、输入均使用美国 10 位号码，不需填写 +1；提交时自动补齐国家代码。未设置专用号码且未绑定注册号码时输入框留空，不显示示例号码。
- 成员管理的短信接收号码在没有专用覆盖值时自动填入已关联账号的注册手机号。开启“接收个人日结短信”时，专用号码和注册手机号至少要有一个有效值；两者均为空时不得保存，并向店长明确提示先填写号码或让员工完成账号注册。
- Mac“信息”代理发送个人日结时，每个任务只发送一张包含姓名、营业日、日结周期和金额的 PNG，不再另外发送重复的文字消息。
- 参与记工的普通员工若尚未出现在当天表格，可在当前营业日点击“上班”把本人加入；不能借此添加其他成员。
- 可从今日表格隐藏员工；有记工者的记录同时隐藏但不删除、不影响财务。“已隐藏员工”管理区位于礼物卡销售下方，可恢复显示。
- 隐藏时若该营业日没有任何记工（包括已删除记工历史），直接移除当天员工行及全部当天上班记录，不进入隐藏列表；之后可重新添加或上班。仅处理所选营业日，日结后仍须先取消日结。
- 重新显示员工时，记录恢复；营业日已日结后必须先取消日结才能调整显示状态。
- 每天默认按加入顺序出现，店长或经理每天可通过上移、下移调整顺序。
- 排序实时同步，记录随员工整行移动。

### 8.3.1 每日开门排位

- 每日开门排位由每家店单独开启，默认关闭；启用前所有在职服务人员必须设置全职或兼职，开启后创建、审批、恢复和修改成员也必须保持该条件。
- 店长或经理把实际上班的员工加入今日表格后点击“添加员工”右侧的“生成今日顺序”（生成后显示“重新生成今日顺序”）。系统使用每人所选日期之前最近一次可见出勤的最终名次：第二变第一、第三变第二，第一移到有历史员工的末尾；人数变化时自动压缩名次。
- 多人竞争同一目标名次时全职优先；同类型按最近出勤日期较近者优先。完全没有历史的新员工排在所有有历史员工之后，新员工之间全职优先。上述条件相同则按固定成员 ID 稳定排列，当天加入名册的时间和先后不参与自动排序。
- 隐藏员工不参与当天排位，历史上隐藏的员工行不算一次出勤。后来加入的员工先在末尾，再次生成后按个人历史位置插入。
- 今天及未来日期未日结时可随时生成或重新生成（过去日期不允许自动生成），即使已经有记工也不受影响；重新生成会覆盖所选日期的手动顺序。未来日期采用所选日期之前已保存的最近可见员工行作为依据，包括已提前安排的更早日期；后续名单变化不会自动重排未来日期，需要再次生成。手动上移、下移后的最终可见顺序是下一次出勤的历史依据。
- 尚无任何打卡或记工（包括已删除记工）的误加员工可以移除；已有活动者不能移除，只能隐藏。
- 排位只改变员工行顺序，不判断下一位、不区分普通客、点名或店方指定，也不产生画叉、欠位或补位；记工、付款、删除恢复、AI 和日结不读写排位状态。
- 只有店长和经理能生成或修改顺序；普通员工可以查看排列后的员工顺序并继续使用原有记工入口，姓名前不显示数字名次。

### 8.4 工作状态

- 今日记工页面只为尚未加入当天表格的普通员工提供“上班”按钮，不提供“下班”按钮。
- “上班”只负责建立本人当天班次并加入今日表格；员工行的可见工作状态不依赖班次结束时间。
- 员工行根据当前时间是否落在记工的开始与结束时间内显示状态。
- 没有进行中的记工显示“空闲”；有进行中的记工显示最晚的“下工时间”。
- 重叠记工取结束时间最晚的一笔；没有结束时间的进行中记工显示“下工时间 · 未定”。

### 8.5 格子显示内容

至少显示：

- 开始时间。
- 结束时间（默认自动计算，可编辑）。
- 项目简称。
- 大费总额。
- 小费总额。
- 大费付款方式。
- 小费付款方式。
- 记工小卡与新增入口统一固定宽度为 177px，左右内边距 6px；时间保持 0.95rem 字号并强制单行完整展示，不截断或省略。
- 记工轨道随员工卡片的可用高度拉伸，小卡与新增入口等高；桌面上下仅留 6px 内边距，减少底部空白。时间使用稍大的 0.95rem 字号，保持完整时间范围可读。小卡内项目、时间和金额组纵向均匀分布，金额组靠近底部内边距，大费与小费间距为 6px，避免内容集中在顶部。
- 今日记工卡片的大费主数字始终显示折前原价（主要项目加额外项目）；后面的付款区域在已确认时显示“实收”及付款拆分，不加外边框；待结账时保留小框，显示“应收”及服务端提供的折后应收金额。实收拆分保留刷卡细线框、现金无框、礼卡文字和混合付款加号；零实收显示 `0`。折扣继续由右上角 `off` 标记表达，待结账仍保留右下角橙色标记。
- 小费保留实际付款方式拆分：刷卡金额加框，现金不加框，礼物卡带“礼卡”文字；零小费显示 `0`，待结账显示“待填写”。详细实收金额仍可在记工编辑器中核对。
- 已确认记录的实际服务付款与应收金额不一致时，卡片右下角显示红色“！”；标记只比较服务付款，不因小费为 0 或小费差异触发。付款异常只发生在已确认记录，与待结账状态互斥，因此两种右下角标记不会同时出现。
- 额外项目只在卡片右上角显示绿色小型“＋”标志，不在卡片底部显示“有加项”文字；可与高亮、折扣和待结账标记并排。
- 折扣标记；今日卡片使用 `off5`、`off10` 这样的红色紧凑标签显示折扣总额，不重复显示货币符号或小数位。
- 待结账状态。

主表格只显示大费总额：

`项目金额 + 额外项目金额`

不显示折扣金额。

### 8.6 待结账

初次创建后使用浅橙色背景。

只有付款信息填写完整并通过统一“保存”按钮确认后才解除。

- 同一员工可以同时保留多笔待结账记录；新建第二笔不得因第一笔尚未结账而报错。
- 多笔记工时间重叠时，员工行显示结束时间最晚的一笔作为下工时间。

- 小费输入 0 表示无小费。
- 小费留空表示忘记填写或尚未填写。
- 草稿状态必须保留“留空”和“明确输入 0”的区别。
- 确认付款时，现金、刷卡与礼物卡大费至少有一项被明确填写；未填写的付款方式自动按 0 保存。混合付款可同时填写多种方式。
- 勾选使用礼物卡后必须填写礼物卡序列号，并分别填写礼物卡支付的大费与小费；两者至少一项大于 0。未勾选时序列号保存为空，礼物卡金额保存为 0。
- 现金、刷卡与礼物卡小费都可以留空，确认时自动按 0 保存。
- 免费或免单记录允许三种大费最终均为 0，但用户仍需在至少一个大费字段中明确输入 0。
- 确认后现金、刷卡、礼物卡的六个付款拆分金额都保存为非空金额。
- 记工详情的普通付款输入按支付方式分成两行：第一行为“刷卡：大费、小费”，第二行为“现金：大费、小费”；手机和桌面保持相同顺序，礼物卡继续使用独立区域。
- 详情页只提供一个“保存”按钮。待结账记录的付款信息完全空白时只保存记工修改并继续待结账；只要任何大费、小费或礼物卡字段开始填写，就校验完整性并在保存详情后确认付款。已经确认的记录再次保存时始终重新校验并同步付款。显式填写大费 `0` 视为已开始填写，可用于免费服务；小费留空按 0 处理。
- 实收服务费与折后大费业绩不一致时显示警告，但不阻止确认。

同时显示：

- 大费总额。
- 小费总额。
- 应得工资。

### 8.8 礼物卡销售

- 每个营业日在所有员工行下方固定显示独立的“礼物卡销售”栏目；当天没有未删除的卖卡记录时自动显示紧凑窄条，高度参照收起的员工栏，只保留标题、零张/实际收入和可编辑时的“记录卖卡”按钮；不显示说明段落、空白提示或大号新增卡片。新增首笔后自动显示完整销售卡片，删除最后一笔后恢复窄条；已日结等只读状态不显示新增入口。手机空间不足时允许按钮换行。
- 新卡表单默认显示每家店从 1001 独立递增的下一张号码；用户可直接改为最长 120 字符的自定义序列号。未修改建议号码时由服务端在事务中自动分配，手动修改时提交自定义号码；软删除也不复用旧号。
- 每笔销售记录礼物卡面值、售出时的折扣门槛/比例快照、折扣金额、实际收款、现金付款、刷卡付款和操作人。操作人从本店在职成员列表选择。
- 店铺可设置礼物卡“满指定面值、按百分比折扣”；`面值 - 折扣 = 实际收款 = 现金 + 刷卡 > 0`，由服务端按整数美分最终校验，客户端即时预览。
- 同一店铺的序列号不可重复；序列号比较使用 Unicode 规范化并忽略大小写、重复空白与首尾空白，已软删除的历史号码也不得重新用于新销售。
- 礼物卡销售沿用记工的营业日写入权限、日结锁、幂等、乐观锁、软删除与审计规则。普通员工只能修改当前营业日，店主和经理可修改未日结的历史营业日。
- 卖卡金额全部计入店铺收入，不产生员工工资或分成；卖卡收到的现金也不进入员工现金结算。
- 礼物卡消费只要求记录序列号和本次使用金额，不自动核销余额；同一序列号可跨多笔记工使用，也允许录入上线前已售出的礼物卡。
- 财务页提供礼物卡台账，按序列号自然排序并展示售出日、面值、折扣、实际收款、售出人、付款方式和同卡多条使用记录。

## 11. 金额定义

设：

- P = 主要项目金额。
- E = 额外项目总额。
- D = 折扣总额。
- CS = 现金大费。
- CC = 刷卡大费。
- GCS = 礼物卡大费。
- CT = 现金小费。
- CCT = 刷卡小费。
- GCT = 礼物卡小费。

### 11.1 大费基数

`大费基数 = P + E`

### 11.2 折后大费业绩

`折后大费业绩 = P + E - D`

统一使用“折后大费业绩”这一名称。

### 11.3 实收服务费

`实收服务费 = CS + CC + GCS`

### 11.4 小费总额

`小费总额 = CT + CCT + GCT`

### 11.5 客人总付款

`客人总付款 = CS + CC + GCS + CT + CCT + GCT`

### 11.6 今日流水

`今日流水 = 折后大费业绩 + 礼物卡销售实际收款 - 礼物卡核销支出`

今日流水只显示在财务汇总的每日小计中，不包含小费、员工收入或实际服务付款拆分，由后端按整数美分计算。

### 11.7 不匹配处理

理想情况下：

`CS + CC + GCS = 折后大费业绩`

允许不一致，仅警告，不阻止保存。可能用于欠款、免单、少收、多收、特殊调整等。

第一版金额输入约束：

- 项目、额外项目、折扣、现金大费、刷卡大费、礼物卡大费、现金小费、刷卡小费、礼物卡小费均不得为负数。
- 折扣总额不得超过大费基数；免费服务可令折扣总额等于大费基数。
- 第一版不使用负数模拟退款或冲正；退款属于后续独立流程。
- 因第一版不包含退款专项流程，本节“不匹配”主要用于欠款、免单、少收、多收和特殊调整。

## 12. 工资计算

### 12.1 主要项目工资

`主要项目工资 = 项目金额 × 最终提成比例`

### 12.2 额外项目工资

每个额外项目单独计算：

`额外项目工资 = 额外项目金额 × 该额外项目最终提成比例`

### 12.3 大费工资

`大费工资 = 主要项目工资 + 所有额外项目工资`

### 12.4 员工应得总收入

`员工应得总收入 = 大费工资 + 现金小费 + 刷卡小费 + 礼物卡小费`

折扣不减少工资。

## 13. 每日现金结算

### 13.1 现实现金流

员工每天会拿走当日全部现金，包括：

- 现金大费。
- 现金小费。

每天关门后，通过“结算今日现金”确定员工应保留和应提交的现金。

### 13.2 现金工资分摊

员工保留的现金部分必须按真实提成计算，不使用固定 60%。

若一单含现金大费以及刷卡或礼物卡大费，则将本单大费工资按全部实际服务费中的现金占比分摊：

`本单现金对应大费工资 = 本单大费工资 × 现金大费 / 本单实收服务费`

若实收服务费为 0，系统需安全处理并提示异常。

现金不足以覆盖上述工资时，不能把员工实际没有收到的钱视为已经取得：

`本单实际通过现金取得的大费工资 = min(本单现金大费, 本单现金对应大费工资)`

`本单现金工资缺口 = 本单现金对应大费工资 - 本单实际通过现金取得的大费工资`

若实收服务费为 0，则本单现金对应大费工资和实际通过现金取得的大费工资均为 0；全部大费工资继续计入老板尚欠。

### 13.3 当日公式

`员工共收到现金 = 当日现金大费 + 当日现金小费`

`员工实际通过现金取得的大费工资 = 各单实际通过现金取得的大费工资之和`

`员工应保留现金 = 员工实际通过现金取得的大费工资 + 当日现金小费`

`员工应提交店铺现金 = 当日现金大费 - 员工实际通过现金取得的大费工资`

员工应提交店铺现金不得为负数。现金工资不足部分继续计入老板尚欠，并在现金结算页面提示。

示例：

- 大费基数 100。
- 折扣 10。
- 客人现金支付大费 90。
- 现金小费 20。
- 项目提成 60%。

则：

- 员工大费工资 60。
- 员工应保留 60 + 20 = 80。
- 员工共收到 90 + 20 = 110。
- 员工应提交店铺 110 - 80 = 30。

### 13.4 结算今日现金页面

主要在每日下班结算时出现；拥有者或经理可返回历史日期重新查看。

每位员工显示：

- 今日现金大费。
- 今日现金小费。
- 今日共收到现金。
- 今日现金对应大费工资。
- 今日实际通过现金取得的大费工资。
- 今日现金工资不足金额。
- 今日应保留现金。
- 今日应提交现金。
- 未结清/已全部结清。
- 备注。
- 结算人和时间。

点击“标记全部结清”直接结算，无需填写备注，也不弹出备注输入框；已有备注仍可查看。

现金结算页面只显示该营业日存在未删除记工记录的员工；完全没有记工的员工不显示，也不进入一键全部结清。

仅两种状态：

- 未结清。
- 已全部结清。

不记录实际提交金额，不做部分结算，不做双方净余额。

支持：

- 单独标记。
- 一键全部结清。
- 取消已结清状态。
- 查看历史。
- 完整操作日志。

### 14.2 尚欠工资

- 实际通过现金取得的大费工资。
- 全部现金小费。

确定公式：

`老板尚欠员工 = 员工累计应得总收入 - 已通过已结清现金结算实际取得的收入 - 工资结算账本累计已支付`

若结果小于 0，界面不显示负数欠款，而显示“老板尚欠 $0”和“已超额支付 $X”。拥有者本人的服务收入不进入老板尚欠和工资结算。

不得与员工应提交店铺现金合并成“双方净余额”。

员工可查看自己的：

- 累计应得。
- 已通过现金获得。
- 老板已支付。
- 老板尚欠。
- 工资结算明细。

### 14.3 员工区间结算资料

财务页向 Owner/Manager 提供独立的员工结算区。选择员工、日期区间和工资来源后，系统从付款已确认且未删除的记工确定性生成预览；允许包含尚未日结的营业日。工资来源分为现金、刷卡＋礼物卡和全部，混合付款按每笔现金付款占比分摊大费工资，刷卡与礼物卡合并为非现金侧。

区间结算资料不创建工资支付、不修改工资结算账本，也不改变老板尚欠。页面所有结算金额显示到美分，不得把小数四舍五入成整美元。页面逐笔列表最多支持 999 笔；超过时必须缩短日期区间，不得静默截断。短信发送记录入口必须紧邻“短信发送长图”按钮，以弹窗展示队列状态、错误和重试操作，不再占用结算区下方的常驻区域。

页面“按日记工”小卡顶部集中展示项目、时间与笔次，中间以对齐行展示大费基数和小费付款明细，不展示大费实收；底部两列展示收入组成，合计独占一行突出显示。当日总结沿用紧凑间距。

员工结算通过 SMS/MMS、RCS 或 iMessage 只发送一张完整逐笔 JPEG 长图。结算不再生成或发送 PDF、独立摘要图，避免 Messages 把文档附件降级为随后失败的 SMS。队列提供“重发长图”，始终使用创建任务时的不可变快照。

短信发送使用创建任务时的不可变快照，只生成一张完整逐笔 JPEG 长图。顶部保留店名、员工、区间、分类、笔数和三张工资汇总卡，下面按营业日分组；每笔记工使用独立卡片，每天以“当日总结”卡片收尾。“当日总结”固定放在当日最后一行的最右列；在两列布局中，当日记工为双数时左侧保留一个空卡片位置，在三列或四列布局中同样补足必要空位后右对齐。同一天记录超过一行时自动换行，项目名称、付款拆分和混合付款提示根据卡片宽度自动折行，不得使用省略号隐藏内容。渲染器根据总天数和记录密度在 1080、1440、1680 像素源画布与 2～4 列之间自动选择布局，再压缩为不超过 4 MB 的 JPEG。长图不含独立封面、页码或重复页眉；最大源高度为 32,760 像素，超过可读上限时要求缩短日期区间。任务只记录这张长图的发送检查点。

财务汇总“关键结果”增加平均营业额，按所选起止日期（含两端）内已日结日期的折后大费业绩与卖卡实际收款合计除以实际已日结天数，沿用当前员工、付款方式、金额类型和高亮筛选，不受30天窗口限制。未日结日期不计入；已日结但无匹配记工及卖卡的日期按零计入分母；不包含小费；卖卡沿用店铺级销售筛选规则（员工筛选、仅大费、仅小费或仅高亮时不纳入），四舍五入到美分。卡片说明显示参与计算的日结天数；范围内无已日结日期时显示“—”。

每日小计按营业日列出“日期、星期、今日流水、过去30天平均营业额、主要项目、加项、大费基数、折扣、折后大费、礼物卡销售、礼物卡核销支出、员工总收入、店铺收入、总收入”。每日小计最后一栏总收入 = 店铺收入 + 店长作为工人的收入 + 所有经理作为工人的收入，由后端按当前筛选范围计算；默认与展开全部列时均显示，不额外加减礼物卡净收入或信用卡手续费。其中日期固定在最左侧，星期紧随其后，再显示今日流水；星期按营业日期计算，随界面语言显示中文或英文，不受设备时区影响，默认与展开全部列时均显示；每日小计不显示全部项目数、记工数、实收服务费、小费或客人总付款。

财务每日小计的“过去30天平均营业额”紧随今日流水，默认和展开全部列时均显示；日期和星期两列采用紧凑宽度。每行沿用记工页全店统计口径：该日期及此前29个自然日内的已日结营业额（折后业绩加卖卡实收）除以实际已日结天数，空日结计零，不含小费，不受财务员工或记工筛选影响，也不被所选起始日期截断。该行未日结时显示“—”；金额提示显示实际日结天数。

汇总卡片不显示“老板尚欠”和“本期工资结算”；财务汇总页面移除“累计余额”区域，工资结算账本与余额计算保持不变。每张保留的汇总卡片必须带圆形“！”说明入口，鼠标悬停、键盘聚焦或触屏点击时显示该词条的解释和计算方法。卡片金额本身仍可点击查看组成明细。

### 15.4 导出

当前支持防公式注入的 UTF-8 CSV 导出、个人日结 PNG 和员工区间结算 JPEG 长图。Excel、PDF 以及独立的可打印现金结算单只保留为产品方向，不承诺已实现。

## 16. 日结

- 全店日结、强制日结和取消日结仅由拥有者和经理操作。
- 不自动日结。
- 不日结也允许进入下一天。
- 可日结、强制日结、取消日结、再次日结。
- 今日记工与历史记工页面均向拥有者和经理显示日结操作：未日结时显示“日结”，先请求服务端预览；没有阻塞项或只有非阻塞提醒时直接提交普通日结，存在真正阻塞项时跳转到同店同营业日的财务日结页面。
- 已日结的今日或历史记工页面向拥有者和经理显示“取消日结”；取消无需填写原因，使用当前有效日结版本执行乐观锁校验。普通员工不得看到这两个操作。

日结弹窗每位员工显示：

- 大费基数。
- 折扣总额。
- 折后大费业绩。
- 小费总额。
- 应得工资。
- 待结账记录提示。
- 金额不匹配提示。

全店显示：

- 全店大费基数。
- 全店折扣总额。
- 全店折后大费业绩。
- 全店小费总额。
- 全店客人总付款。
- 礼物卡销售张数、现金、刷卡和销售总额。
- 店铺收入（包含礼物卡销售）。

必须重点显示：

- 每人折后大费业绩。
- 每人应得工资。
- 全店折后大费业绩。

日结前检查：

- 待结账记录。
- 小费留空。
- 金额不匹配。
- 异常负数。
- 未填写结束时间。

日结非阻塞提醒：

- 手动改价必须显示提醒并提供对应记工的查看入口，但不阻止普通日结，不禁用“确认日结”按钮，也不单独显示强制日结入口。

允许强制日结。

全店日结页面的每类异常必须提供对应记工的直接查看入口。入口携带店铺、营业日和记工编号，打开今日/历史记工页后自动定位并打开该笔详情，避免只显示异常数量却无法排查。

### 16.1 个人日结

- 卡片内员工姓名右侧集中显示生成日结图片、保存/分享、短信发送按钮以及成功或失败提示；窄屏空间不足时自动换行，生成图片预览保留在逐笔记工下方。

- 店主和经理在个人日结页面始终可逐人发送短信，不要求先完成全店日结；仍需开启成员短信接收并设置有效号码。未日结任务保存发送当时快照，不随后续记工更新；批量发送仍要求全店日结。未日结时，记工页与财务日结页也显示短信队列，允许查看进度和取消排队任务。
- 现金交接下方显示“已结现金”状态，表示店里已发放该员工当天现金大费工资，现金小费由员工自行收取。店主和经理可标记或取消；员工只读。沿用每日现金结算记录、版本与财务现金页状态，不新增工资支付记录；无记工时不提供操作。
- 取消已结现金无需填写原因；修改相关记工、提成或取消日结后，已有现金标记按现有规则回退，需要重新核对。


- 今日页面的每个员工行提供“个人日结”入口；拥有者和经理可打开任意员工，普通员工只在自己的员工行看到入口。
- 财务页向员工提供“我的日结”标签，但后端响应只包含本人合计与本人异常，不包含全店合计、其他员工数组或他人的记录编号。
- 个人日结页面和 Mac 代理 PNG 都用二维汇总表整理已确认收入：大费工资和小费工资分别按现金、刷卡和合计展示，今日总收入在同一白色汇总区内独立突出。待结账记工不进入这些已确认收入。
- 现金交接在页面中固定显示在逐笔记工之前；生成的网页 PNG 和短信 PNG 不展示“大费基数／现金大费”汇总栏。个人日结不显示“请先核对”提示区；待结账状态仍在对应逐笔记录上明确标识。
- 个人日结随后按开始时间展示该员工当天每一笔记工，包括主要项目、加项、状态和本单收入。逐笔的“员工大费（折前）”必须使用 `grossFeeBaseCents`，不得使用减去折扣后的实际大费付款；现金、刷卡、礼物卡的大费实收拆分仅作为次级付款信息。代理图片中的现金金额直接显示，刷卡金额使用细线圆角框，礼物卡金额追加括号说明，零金额不占位置。
- 个人日结不显示折扣金额。员工接口只返回目标员工自己的记录，不加载全店或其他员工数据。
- 个人日结的“现金大费”显示店里应发给员工的现金大费工资，读取 `cashLargeFeeDividendCents`：前台收取全部现金大费，按项目折前金额和各自提成比例计算工资；混合付款按现金占全部实收服务费的比例分摊。折扣由店里承担，不扣员工提成；现金小费由员工自行收取，不计入这笔应发金额。此处不再展示旧的员工上交店铺四成金额；旧接口字段和财务现金结算兼容口径保留。
- 现金大费分红为已确认记工按现金付款占现金、刷卡与礼物卡全部服务费的比例分配的工资，非现金大费分红为未通过现金分配的剩余工资（包括刷卡、礼物卡与免费项目仍应获得的工资）。现金小费单独汇总，刷卡与礼物卡小费合并为非现金小费。四项相加等于已确认记工的大费工资与小费合计。
- 个人日结图片将今日总收入设为浅色背景、深色大字；逐笔卡片左侧展示项目、时间、状态、折前员工大费与本笔收入，右侧紧凑展示大费实收和小费。长项目及付款内容自动换行。网页图片按当前设备宽度和像素密度生成，高度随实际内容计算，不再补足整屏空白；记录较多时自动增长为长图，确保逐笔记工与付款不会被截掉。支持文件分享的手机通过系统分享菜单保存到相册，其他浏览器降级为下载 PNG。

## 18. 多设备实时同步

同一账号登录不同设备与不同账号登录同店均自动同步，正常前台连接目标为保存后约 2–3 秒加请求耗时更新数据。保留当前日期、滚动位置与未保存编辑；遇到并发修改沿用版本冲突提示。页面隐藏/离线时暂停实时同步，恢复前台或联网后补读；连接卡住 10 秒会重连，异常期间以 30 秒间隔重试。“已同步”表示已收到实时消息且最近的数据读取成功，不以 HTTP 连接打开作为成功依据。


必须支持：

- 同账号多设备登录。
- 手机、iPad、电脑实时同步。
- 新增、修改、删除、排序、上下班、日结和结算状态实时更新。

必须处理：

- 双击重复提交。
- 重复请求。
- 网络中断。
- 保存失败。
- 两人同时编辑。
- 旧页面覆盖新数据。

实现要求：

- 唯一记录 ID。
- 幂等请求键。
- 乐观锁版本号。
- 更新时间戳。
- 冲突提示。
- 明确保存失败状态。

## 19. AI 记工助手

同一会话支持连续追问：助手接收之前已保存的提问、回复、查询结果和预览，用于理解补充信息和指代。财务助手同样支持沿用前文日期、员工及金额范围，再查询最新统计。不同用户、店铺或助手类型不能共用会话；角色变化后不沿用原权限下的结果。旧版本未保存的完整回复无法补回，刷新页面暂不自动恢复会话。未配置模型时仍按单句安全降级处理。

### 19.1 能力

支持中文和英文文字/语音输入。

- 记工助手提供显式语音按钮，每段录制 6–60 秒；转写结果回填输入框，允许用户修改后再发送。
- 语音识别调用 MiniMax `music-cover` 音频预处理接口内置的 ASR，与文字理解共用 MiniMax API key；浏览器或模型不支持时保留文字输入和系统键盘听写。
- 原始录音上限 8 MB，只在请求内存中流转，不持久化。

可理解：

- 员工姓名。
- 项目。
- 时间。
- 金额。
- 额外项目。
- 折扣。
- 混合付款。
- 小费。
- 修改哪一条记录。

### 19.2 工作流

1. 理解自然语言。
2. 生成结构化预览。
3. 展示完整预览。
4. 用户确认。
5. 在同一事务中写入详情、付款、审计并消费预览；失败全部回滚。

AI 不得直接执行任意 SQL。

员工通过 AI 操作其他员工记录时，必须明确姓名并展示完整预览。删除必须二次确认。

### 19.3 微信群记工助手

指定 WeChatPad 机器人通过 LangBot 接入微信群，支持绑定、记工、受限查询、按编号管理、多人原子操作及插件内澄清。完整行为和示例以 [机器人手册](../operations/LANGBOT_WORK_BOT.md) 为准。

- 由流水线限制为群内 @ 专用机器人；群绑定店铺，发送者绑定在职成员，历史权限另由管理者核实。保留原因：路由范围和姓名认领不能代替真实身份与角色鉴权；未参与记工的管理者仍可绑定查账。
- 模型每次读取实时目录和店铺说明，员工、项目、时长、付款与金额均由原文证据和后端契约复核。保留原因：口语理解不能成为任意金额、跨店操作或虚构对象的来源。
- 上工开始时间按原文与店铺时区解析，未指定时回退消息时间；下工与调整复用现有记工，未指定编号时要求唯一待付款记录。保留原因：同一员工可能有网页创建的多笔记录，不能把机器人占用指针误当全部业务记录。
- 下工实收不覆盖项目原价；混合付款、礼物卡及历史管理使用现有受限管理意图。保留原因：实收、折后业绩与工资不同，旧版仅支持现金或刷卡的限制不再代表完整协议。
- 写入保留权限、日结锁、事务和消息幂等；多人指令全部校验成功才提交；澄清确认只学习、不记账。保留原因：避免半笔账、重放和把纠正消息误当业务授权。

## 20. AI 财务助手

- 财务页面提供 AI 聊天入口。

## 21. 数据与快照要求

精确表、字段、索引和约束以 `packages/database/prisma/schema.prisma` 与向前迁移为准，产品文档不复制一套易过时的数据库清单。数据模型必须覆盖：

- 用户、店铺、成员关系和加入审批。
- 每日班次、员工行、项目目录和提成规则。

- 礼物卡销售和按序列号关联的每次使用记录。
- 日结、现金结算和工资结算的独立状态或账本。
- 审计、幂等请求、实时 outbox 和 AI 预览/查询日志。

明细与必要的历史汇总快照可以同时保存，但所有写入汇总都由服务器从明细重算，不信任前端最终合计。数据库约束、事务、乐观锁、幂等、软删除和同事务审计共同保证可追溯性。

- 全站基础字号 19px，普通辅助文字至少 0.85rem；常用操作按钮至少 48px 高，保留明显键盘焦点。压缩装饰留白，不通过缩小文字提高密度。
- 财务汇总默认展示总流水、店铺收入、总收入和项目数量。项目业绩、收款、礼物卡和店铺总结算构成可分别展开；25 个指标、解释和计算口径完整保留。
- 日期快捷按钮直接查询；自选日期和更多筛选需点击“查看结果”。结果区域标明已查询日期；导出采用当前已展示结果的条件。
- 每日小计默认展示日期、星期、今日流水、过去30天平均营业额、员工总收入、店铺收入；“显示全部列”展开项目、折扣及礼物卡明细。宽表只在自身容器内滚动。
- 记工员工行保留直接“个人日结”入口，排序、移除与隐藏统一放入“员工操作”，展开后再执行。“员工操作”和“更多操作”每次展开后 10 秒自动收起，再次展开重新计时。底部首页导航名称为“记工”（英文 Work log）。
- 工资页将“生成区间结算单”与“登记已付工资”分开，登记表单按需展开，减少误把查看结算单当作工资付款的混淆。
- 手机财务功能导航换行展示，现金卡按两列金额排列；中文和英文共用响应式布局。日结、现金和工资写入规则与权限保持不变。

- 底部固定导航按实际渲染高度在页面末尾留位，支持语言换行、缩放及设备安全区；滚动到底后，最后一行内容与导航之间保留 16px 间距。

- 记工详情只选一次服务日期，起止时刻共用该日期；改变日期时按项目总时长重新计算结束时刻。若联动越过午夜则提示调整，禁止保存跨日或结束早于开始的详情；旧跨日草稿保留并要求调整开始时间、结束时间或项目时长，不静默改写历史。项目与金额单独分区。

- 记工页已日结时，操作顺序为发送员工小结、浅色短信队列按钮、深棕色现金结算、取消日结。现金结算进入财务对应店铺和所选营业日的现金标签；短信队列按钮始终显示已发送条数，详情及取消排队操作通过弹窗查看，不再常驻表格上方。未日结时也保留短信队列入口。短信队列弹窗独立于“更多操作”菜单，菜单在 10 秒后自动收起不影响弹窗；用户通过关闭按钮、Esc 或点击弹窗背景关闭，关闭后页面恢复可操作。


## 响应式页面规范

- 手机优先展示当前任务，沿用现有暖色品牌；正文 17px、桌面 18px，输入框至少 16px，主要触控目标至少 44px，并允许浏览器缩放。
- 全站语言切换位于页首正常文档流，不悬浮覆盖标题或表单。手机底部四项主导航根据实际高度预留内容空间；手机和平板的 AI 入口随页面内容排列，点开后显示对话面板。
- 今日/历史页在电脑端（宽度大于 900px）按营业额、平均营业额（已日结且有统计时）、折扣、礼物卡、店铺收入、总收入的顺序展示完整单行汇总，不使用折叠；900px 及以下先显示营业额与总收入，其他金额通过“更多汇总”展开。日结或现金结算是主要操作，发送员工小结、短信队列、排位及取消日结按原权限放入“更多操作”。
- 财务与管理分区使用可横向滑动的单行标签；业务表格和记工卡片仅在自身容器内横向滚动。手机表单纵向排列，日期与付款的关联字段按可用宽度分组。
- 手机、平板、桌面及中英文共用同一套业务组件，不复制金额计算、权限或写入逻辑。

### 定时日结与首次日结发送

API 按店铺设置的时区，在每天 23:30 所在分钟检查当天是否可以日结。只有日结检查完全无异常（包括非阻塞的手动改价提醒）才自动日结，不强制跳过问题。已日结以及取消过日结的日期都不会被定时任务重新锁定；仍可手动日结。无营业记录的日期也可正常日结。该分钟服务不在线时不补结历史日期。

每个营业日第一次成功日结（含手动、强制和自动）自动排队发送员工小结。在职成员开启“接收个人日结”、具有有效接收号码且当天至少有一笔未删除记工才会发送；无当天记工的成员不排队；号码优先使用成员的专用接收号码，再回退账号号码。当天任意小结任务已发送、排队或发送中均跳过，包含日结前的逐人发送。不符合条件的成员跳过，不影响日结。取消后再次日结不会自动补发，需要使用既有手动发送功能。

自动发送沿用现有 Mac“信息”代理，代理离线时任务保留排队，实际发出时间以代理处理为准。日结及自动发送任务原子保存，避免任务漏建或并发重复创建。

发送代理逐条处理日结及区间结算任务，每条任务处理结束后（包括失败）至少等待 60 秒，再领取下一条任务，避免连续密集发送。发送结果不明确仍需人工核对，不自动重发。

明确指定多位员工的机器人指令同时操作各人，例如“Ling Jessie 上工 大力”。多人写入保持原子性，任一人校验失败则全部不执行；下工金额不得把合计复制为每人金额。

可重试的发送失败固定等待 60 秒后重新排队领取，最多重试 3 次（首次发送加重试共 4 次）；达到上限标记失败，停止自动重试。队列繁忙或代理离线时实际重试可能更晚。已交给“信息”但结果不明确的任务仍需人工核对，不自动重发。
