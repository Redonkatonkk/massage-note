# 产品与业务规则

> 状态：当前产品规则 · 适用版本：`1.18.7`
> 核对依据：领域函数、共享契约、API 服务及其测试。HTTP 字段见 [API](../engineering/API.md)，布局见 [UI 设计](../engineering/UI_DESIGN.md)，维护流程见 [开发指南](../engineering/DEVELOPMENT.md)。

## 产品范围与数据原则

- 提供多店铺、三角色、中英文响应式 Web 记工与经营核算，支持手机、iPad、电脑及多设备登录。保留原因：这是现有页面、成员作用域与实时接口共同支持的产品范围。
- 持久金额使用整数美分，提成使用万分比，最终财务计算使用 domain 函数；显示格式不改变账本。保留原因：浮点数、前端合计和模型回答不能作为金额真相。
- 普通记工及概览通常显示整美元；工资结算、支出、对账图片等使用现有精确格式，编辑保留真实美分、不自动补 `.00`。保留原因：`formatUsd` 与 `formatUsdPrecise` 有不同用途，笼统要求所有只读金额取整会丢失对账精度。
- 记工保存名称、时长、价格、折扣、提成及来源、工资、时区和营业日快照；目录变化不改写已日结历史。保留原因：历史账目需要按发生时内容追溯，允许的当前日重算另走受控服务。
- 记工、卖卡、工资、目录和成员等业务对象沿用软删除与恢复；关键写入保存操作人、前后值、请求编号及事务内审计/outbox。保留原因：恢复和账目追溯依赖这些记录；无活动员工行的物理移除是明确的既有例外。
- 语言默认简体中文，选择在本机保存；英文显示可翻译自定义目录名称，编辑和历史快照仍保留原文。保留原因：语言切换属于展示，不能成为改账操作。

## 账号、店铺与成员

- 使用美国十位号码，内部标准化为 E.164；首次由 Firebase 验证手机号并设置姓名及密码，老用户可用密码或验证码登录。保留原因：当前认证链路同时支持 Phone Auth 与密码换 Custom Token，不能继续只记验证码流程。
- 支持退出本设备和撤销全部会话；普通退出保留本机 Firebase 可信状态与偏好，同号码可恢复登录。保留原因：两种退出有不同效果，共用设备解绑须使用撤销全部会话或清理浏览器数据。
- 登录重发倒计时、reCAPTCHA 与接口限流沿用当前实现；账号状态接口返回是否存在及是否设置密码。保留原因：登录页据此选择注册或密码流程，旧文档的“绝不披露是否注册”和独立错误锁定承诺不符合当前接口。
- 创建店铺使用全局唯一六位代码、名称、时区及全局默认提成，再设置目录；时区默认来自设备。保留原因：店铺代码负责加入定位，店铺时区负责没有设备上下文的日期计算。
- 同一账号可在不同店铺持有不同角色，每店唯一 Owner；Manager 可管理成员、目录、记工和财务，也可指定经理，但不能修改/移除 Owner、转移店主或删除店铺。保留原因：权限按成员关系授权，所有权有单独的原子转移流程。
- 店主转移目标必须是本店在职且关联有效账号的成员；角色与是否参与记工独立。保留原因：未认领/停用账号不能接管，管理权限不应决定是否能提供服务。
- 参与记工的经理正常进入工资与欠款；Owner 的服务收入单独核算，不进入给自己的工资结算或老板尚欠。保留原因：经营收入与雇员债务是不同口径。
- 所有活跃成员可查看和修改当天记工，包括其他员工；员工历史只读本人，不能读取全店财务、管理目录或执行结算。保留原因：当天协作记工与历史工资隐私由不同权限边界保护。
- 店主/经理可预建未注册成员，姓名必填，账号可空，允许记工和配置提成；每日排位开启时全职/兼职必填。保留原因：现有成员 ID 承载历史，排位算法另需用工类型。
- 加入时按账号注册 First Name 与待认领成员的规范化姓名精确匹配，成功绑定原成员，否则提交审批；不能用临时填写的名字冒领。保留原因：保留原 ID、记工及财务，同时避免表单姓名成为身份凭据。
- 在职显示名规范化后唯一；停用仅停用成员关系，恢复保留历史。保留原因：同名会使目录及机器人定位歧义，删除账号或历史会破坏审计。
- 成员管理先选员工再编辑；资料/工资、项目提成、账号状态分区，新增、审批、停用、恢复使用独立确认表单；保存只调用变化的接口。保留原因：当前 `members-panel.tsx` 的任务边界和版本接口需要分别维护。
- 切员工、分区或离开页面保护草稿；实时新版本/停用不覆盖输入，冲突后重新载入核对，资料成功但提成失败时保留已提交版本。保留原因：两个保存接口不能用旧版本重复覆盖，输入也不能因同步丢失。
- 短信号码输入美国十位号码，保存 E.164；专用号码优先，空时回退注册号码，开启接收必须有有效号码。保留原因：未认领成员可能无注册号码，发送任务不能依赖示例占位值。

## 营业日、日历与写入

- 今日取设备时区的自然日期，午夜换日；新记工按开始时间归日，跨午夜结束不改变归属；无设备请求回退店铺时区。保留原因：`device-time.ts` 与 `business-day.ts` 已不使用关门截止倒推日期。
- 已有记录仅在明确修改开始时间时重新归日；旧截止字段保留接口及快照兼容。保留原因：改金额不能移动历史营业日，旧客户端和数据库仍读取该字段。
- 店主/经理可查看未来排工和未日结历史；员工只能查看今天及本人过去日期，不能改历史；记工、跑客、日结与现金结算仍各自限制未来写入。保留原因：提前排工权限不等于提前记账权限。
- 已日结记工先取消日结再修改；取消或相关修改回退现金结清，工资账本保留并重算尚欠，操作写审计。保留原因：已发工资是真实支付，不能因重新开账而自动删除。
- 写入保留权限、对象归属、营业日锁、版本、幂等和事务；409 后由用户核对，不自动提高版本重发旧字段。保留原因：并发、重放和跨店请求不能造成半笔账或覆盖新资料。
- 日历标记有效记工但未日结的日期；已日结日显示折后服务业绩加卖卡实收，员工仅得本人有记工日期及本人金额，取消日结恢复圆点。保留原因：日期标记也有财务信息，必须按角色隔离。
- 记工页按店铺/月缓存最多十二个月，合并同月请求；切日期复用目录和成员，只重读目标表格；本机写入、手动刷新、跨日失效，自动同步/重连只刷新业务，财务日历打开时读取。保留原因：当前缓存明确以手动刷新更新其他设备的日历变化，旧自动失效要求会重新产生重复请求。

## 目录、提成与折扣

- 主要项目含名称、简称及多个不重复时长价格档，共用排序、启用状态及项目提成；加项可有独立金额、时长和提成。保留原因：价格属于时长档，项目身份与专属提成不应随时长拆成多个对象。
- 加项允许本单自定义，留空/零分钟不加时，1–720 分钟保存快照；API 明确 `null` 表示不加时，省略才取目录默认。保留原因：本单调整与预设值有不同语义。
- 标准提成依次为员工项目专属、员工默认、项目默认、店铺默认；自定义项目只取员工默认再店铺默认。保留原因：领域函数按此顺序解析并保存最终来源。
- 员工不能改本单提成，管理者可改并审计；保存员工提成重算其未日结当前日，相关现金结清回退，已日结和更早日期保留。保留原因：当前日调整是已有受控例外，不能泛化成重写历史。
- 固定及比例折扣可多项并用，正数表示减免，无需审批；比例为 0–100%、最多两位小数，每项按同一折前项目加加项金额计算并舍入至美分，合计不超过大费基数。保留原因：比例不含小费，也不按逐次扣减后的余额复利计算。
- 折扣由店铺承担，不减少工资；比例和金额都保存快照，本单项目变化时重算比例，目录变化不批量改历史。保留原因：工资基数与折后业绩独立。
- 周一至周四自动折扣在店铺开启、非高亮且折前金额达门槛时生成，可与手动折扣并用；单笔移除/恢复持久保存停用状态。保留原因：网页与机器人共用判断，单笔停用不应关闭全店规则。
- 高亮新建/编辑排除自动折扣，取消高亮重新判断但不解除手动停用；手动折扣和实际付款保留。保留原因：高亮影响折扣及手续费，不能把展示切换当成重新收款。

## 记工与付款

- 快速创建选择时间、预设时长价格或完整自定义项目，可选高亮；付款、加项、折扣、备注可稍后补，初始待结账。保留原因：现有快速流程只要求开始服务所需信息。
- 同一员工允许多笔待结账；记录按开始时间排序，工作状态取当前进行中记录的最晚结束时间，到预计结束即空闲。保留原因：付款状态和是否正在服务不同，机器人占用指针也不能代表全部网页记工。
- Web 详情起止时刻共用显式服务日期，项目或加时变化按当前总时长联动；手填结束反算开始，跨日/结束早于开始提示纠正。API 省略结束仍沿用保留实际时长加配置差值的兼容逻辑，明确 `endAt` 优先。保留原因：当前前端总时长联动与旧客户端 API 兜底不同，文档不能承诺后端不存在的统一重算。
- 详情与付款使用统一保存：付款全空仅保存待结账详情，有任何付款输入则校验并确认；已确认记录保存始终同步付款，全部在同一事务完成。保留原因：保存详情成功而付款失败不能留下一半更新。
- 草稿区分空白和明确零；确认时至少明确一项大费，其他方式及空小费按零保存，免费项目可明确填零。保留原因：忘记填写与真实零元付款必须区分，确认后六项金额均非空。
- 礼物卡使用须填序列号，礼物卡大费或小费至少一项大于零；未使用时序列号空、金额零；现金/刷卡/礼物卡允许混合。保留原因：台账关联与现金工资分摊需要完整付款拆分。
- 项目、加项、折扣及各类付款不得为负，实收服务费可与折后业绩不一致，只警告、允许确认。保留原因：当前支持少收、多收、免单等事实记录，负数退款没有独立业务流程。
- 记工卡大费主数字显示折前项目加加项，付款区显示已确认实收或待确认应收；小费独立拆分，刷卡加框、现金无框、礼卡标识，折扣用 `off`，加项和备注保留各自标记。保留原因：原价、应收、实收和工资不能混为一个数字。
- 已确认服务付款差额显示异常，与待结账标记互斥；高亮持续使用灰绿色，悬停/只读保持颜色。保留原因：状态应同时由文字和标记辨别，样式不能遮蔽财务异常。
- 删除只确认、不强制输入原因；软删除排除普通页面及统计，由管理者恢复并保留删除快照。保留原因：恢复仍需日结锁与版本，删除不能损失审计内容。

## 员工行、每周排工与轮转

- 管理者可添加员工，空表允许按勾选顺序多人添加；中途失败停止后续、刷新成功项并保留未完成选择；员工上班只能加入本人。保留原因：此 UI 批量沿用逐次写入，不能错误承诺与机器人原子批量相同。
- 隐藏有记工的行不删除记录、不影响财务；当天无任何记工（含删除历史）则移除行与班次，之后可重新添加；已日结先取消。保留原因：误加空行可清除，有业务历史的行必须可恢复。
- 员工顺序用上移/下移，记录随整行移动；每周模板仅管理在职服务人员，星期一至日重复，保存立即生效。保留原因：当前界面不提供拖动排序，模板初始化与人工顺序有独立来源。
- 模板当前日只初始化，未来日按最新名单更新，历史/已日结跳过；取消安排只移除无记工/班次的自动行，手动加入保留。保留原因：模板更新不能删除实际出勤或人工安排。
- 单日手动移除优先于模板，刷新不加回；未来手动调序后保留相对顺序，新成员追加，主动重新生成才恢复自动更新；无变化不写版本/审计。保留原因：看板审计版本记录了最新人工意图，刷新不能覆盖它。
- 弹窗“应用”覆盖所选今天/未来日期的全部排工，不保存模板；有任何记工（含删除历史）、已日结或过去日期则全部回滚。保留原因：一次性覆盖不能破坏记工关联，结果也不应再被自动模板替换。
- 每日开门排位默认关闭；开启要求所有在职服务人员有全职/兼职，管理者可生成今天/未来顺序，不改变逐笔记工。保留原因：轮转只组织员工行，没有逐工派工状态。
- 轮转取每人最近可见出勤位置，原第二及以后前移一位，原第一排在其他有历史人员之后，无历史最后；同位依次全职优先、最近日期优先、稳定成员 ID。保留原因：`rankRotationCandidates` 需要确定性结果，不能按消息到达或输入顺序随机裁决。
- 生成时保存解释快照；手动调序或资料变化不改写原因，旧空快照不推测回填；管理者可导出当前语言完整 PNG，超长分图。保留原因：解释应复现当时决策，而非用今天的资料重算历史。

## 礼物卡与跑客

- 卖卡独立于员工记工，每店默认从 1001 原子递增，也可提交最长 120 字符自定义号；Unicode 规范化后忽略大小写及空白，删除历史号码不复用。保留原因：并发与历史防重不能靠前端建议号保证。
- 卖卡保存面值、折扣门槛/比例与金额快照、实收现金/刷卡和操作人；实收合计须大于零，可不同于折后应付，保存时提醒。保留原因：应付是定价规则，收入必须取实际收到的钱。
- 卖卡实收全部进入店铺收入，不分配员工工资或现金结算；用卡大费加小费为礼物卡核销支出。保留原因：发行收款与服务时用卡需要各计算一次。
- 礼物卡可跨多笔使用，不自动核销余额；已确认有效使用按规范化号码归组，无销售登记的老卡也入台账，但销售资料未知、不补造收入。保留原因：现有台账记录使用事实，没有完整的余额账户。
- 卖卡沿用记工的当前日/历史权限、日结锁、版本、幂等、软删除与审计。保留原因：销售也形成账目，不能绕开营业日保护。
- 跑客记录设备墙上时间、1–999 人（默认一人）及最多 500 字去空白备注；可编辑或软删除，未来不可写，已日结只读；当前所有成员可读写，历史仅管理者。保留原因：人数、时间和备注是独立经营事实，需要版本和审计但不形成财务金额。
- 跑客仅进入经营数量统计，不增加记工、收入、工资或卖卡。保留原因：未成交客人没有服务付款。

## 金额与经营汇总

设 P 为主要项目、E 为加项合计、D 为折扣；CS/CC/GCS 为现金/刷卡/礼卡大费，CT/CCT/GCT 为对应小费。以下公式由领域函数执行。

| 口径 | 公式/约束 | 保留原因 |
| --- | --- | --- |
| 大费基数 | P + E | 工资和卡片原价按折前金额计算。 |
| 折后大费业绩 | P + E − D | 折扣影响业绩，不能改写实收事实。 |
| 实收服务费 | CS + CC + GCS | 付款比例需要三种方式共同组成分母。 |
| 小费/客人付款 | CT + CCT + GCT；实收服务费 + 小费 | 小费与大费分开，工资及现金归属不同。 |
| 大费工资 | 每个项目金额 × 各自最终提成，分别舍入后合计 | 多项目可有不同提成，不能整体乘一个比例。 |
| 员工总收入 | 大费工资 + 全部小费 | 折扣由店铺承担。 |
| 营业额 | 折后大费业绩 + 卖卡实际收款 | 卖卡实收应纳入经营收入，小费另算。 |
| 礼物卡核销支出 | GCS + GCT | 礼卡服务与小费均消耗店铺已经收到的卡款。 |
| 今日流水 | 营业额 − 礼物卡核销支出 | 财务每日小计采用此口径，不含小费。 |
| 店铺收入 | 营业额 + 小费 − 员工收入 − 礼卡核销 | 员工所得和用卡支出均须扣一次。 |
| 看板/每日小计总收入 | 店铺收入 + Owner 服务收入 + Manager 服务收入 | 管理者作为服务人员的收入纳入经营核算，不扣手续费。 |
| 信用卡手续费 | 所选普通刷卡金额合计 × 2.5%，舍入到美分；含所选刷卡金额的高亮每笔 $3 | 部分刷卡也算一笔；无刷卡、高亮零刷卡、礼卡和卖卡刷卡不收费。 |
| 财务总结算总收入 | 店铺收入 + Owner 服务收入 + Manager 服务收入 − 信用卡手续费 | 与看板手续费前口径不同，礼卡净收入不能再加减一次。 |

- 店铺汇总只给 Owner/Manager，按未删除记工计算，隐藏行不影响；看板含待结账已知工资/小费，个人已确认收入另取已付款。保留原因：界面可见性和已确认程度不是同一统计范围。
- 汇总/明细/CSV 共用日期、员工、现金/非现金/全部、大费/小费/全部、高亮筛选；默认全部，最近七天含今天，本月按自然月。保留原因：导出及组成明细必须对应同一查询结果。
- 卖卡只纳入管理者、未限定员工、全部金额且不限定仅高亮的店铺查询；不分摊给员工。项目数量为记工加销售张数，客人总付款包含卖卡实收。保留原因：销售属于店铺，员工或单一金额筛选不能混入无法分配的收款。
- 员工小计显示当前默认提成与专属比例差异，不从工资反推；每日小计保留日期、星期、流水、平均营业额及组成，前端不另算。保留原因：历史工资可能使用多个快照比例。
- 看板及每日行的近三十天平均仅在该日已日结时显示，窗口为该日和此前二十九天；仅已日结日计分母、空日结计零，不向窗口外补足，不受财务筛选/起日截断。保留原因：这是全店经营参考，与当前筛选的汇总平均不同。
- 财务汇总平均按所选范围内已日结日与当前筛选计算，不限三十天，无样本为“—”；营业额含卖卡实收、不含小费，平均舍入到美分。保留原因：未日结不是零收入样本，不能混入平均分母。
- 当前导出为防公式注入 UTF-8 CSV、个人日结 PNG、区间结算图片；Excel/PDF/可打印现金单没有现行实现。保留原因：文档不能把旧产品方向当作已支持功能。

## 现金、每日全额结清与工资账本

- 现金对应大费工资按本单大费工资 × 现金大费 / 全部实收服务费分摊；实收为零则现金工资为零，剩余工资仍待付。保留原因：混合付款及免费项目不能使用固定六成或除零。
- 实际现金取得工资为 min(现金大费, 现金对应工资)，应留为实际取得工资加现金小费，应交为现金大费减实际取得工资，缺口继续欠付。保留原因：员工没有收到的钱不能记为已取得，提交现金也不能为负。
- 现金结算只含当日有有效记工者，支持单人/全部结清、回退、历史明细和审计；状态只有未结/已结，不记部分交款或双方净余额。保留原因：现有现金状态与工资支付账本分开，不能用一个净数抵掉两种义务。
- 普通个人日结“现金大费”表示店里应发的现金工资 `cashLargeFeeDividendCents`，现金小费由员工自行收取；旧应交字段仅为财务兼容保留。保留原因：个人页面的发薪口径已经变化，不能继续解释为上交四成。
- `dailySettlementEnabled` 默认否；开启后当日应发为全部已确认大费工资加非现金小费，不含员工直接取得的现金小费。保留原因：全额每日发薪与普通现金结清有不同发放范围。
- 全额结清保存设置、额外已发工资及非现金小费快照，日历两来源结清、未结归零，余额计实际所得，不另建重复工资账本；待结账或已有工资确认阻止重复发放。保留原因：同笔收入不能通过两个结清入口重复支付。
- 后改成员设置不改已结快照；取消结清、取消日结或改当天记录使快照失效，其他工资确认保留，重结按现状计算。保留原因：支付历史和新的成员默认值不能混用。
- 工资账本仅管理者操作，排除 Owner，表单为员工、首尾均包含的日期范围、精确金额、现金/非现金/全部来源；默认本月一日至今日，可部分或超额支付。保留原因：真实付款金额与工资来源必须独立记录。
- 登记日按设备日期自动保存，编辑保留原登记日；版本、删除/恢复、操作人及审计沿用；历史未知来源不猜测，旧拆分请求继续兼容。保留原因：实际支付方式不能推出工资来源，也不能伪造旧账拆分。
- 尚欠 = 累计应得 − 有效现金结清实际所得（含有效全额结清附加支付）− 工资账本支付；负数显示欠零和超付，员工只读本人。保留原因：欠薪与员工应交现金独立，Owner 不形成对自己的债务。

## 区间结算与发送

- 管理者选择员工、含首尾的日期范围和工资来源，从有效已确认记录生成完整结算，可含未日结日，最多 999 笔；Owner 仅生成资料。保留原因：资料不是支付授权，超限需缩短范围而不能截断。
- 现金/非现金工资按本单付款比例分摊，非现金包含刷卡、礼卡及未通过现金分配的工资；已结记录仍进入资料。保留原因：结算单说明完整期间收入，不仅剩余待付部分。
- 日历黄色表示现金确认，绿色表示非现金确认，全部贡献两侧，无相关来源不标；现金结清有缺口时仍可标黄但缺口待付。保留原因：业务确认与实际取得金额分别表达。
- 本次未结排除有效确认范围并扣除每日现金实际所得；抵扣手填、默认零、不得超过未结，本次实付为未结减抵扣。保留原因：历史付款无法自动推断日期分配，手工抵扣不能造负支付。
- “已付款”按预览 revision、幂等键与营业日锁原子保存实付及确认，可零实付；空记录、Owner、全已结或旧 revision 拒绝，重叠范围只付未结部分。保留原因：用户核对的收入发生变化后不能继续按旧预览支付。
- 确认关联账本，编辑、删除、恢复同步改变贡献；手工/旧账本不自动推测确认，其他有效确认保留。保留原因：金额支付不等于指定日期和来源全部结清。
- Web 可本机生成/保存当前语言完整 PNG；变更员工、范围、来源、语言或刷新清除旧图，不入短信队列、不登记付款。保留原因：图片必须对应当前预览，生成资料没有业务副作用。
- 日结短信使用单张 PNG；区间短信使用带三张汇总卡、每日总结及完整逐笔明细的单张 JPEG，按创建任务不可变快照重发。保留原因：已入队/已发资料不能随之后记工或模板变化改写。
- 区间“当日总结”固定为每天第一张、最左列，记录随后按时间排列，无补空位；容量/路由与冷却要求集中于 [代理手册](../operations/MESSAGES_AGENT.md)。保留原因：共享 SVG 和现有测试已采用此顺序，旧最右列规则已失效。

## 日结与自动发送

- Owner/Manager 可普通、强制、取消和再次日结，不日结可进入次日；现金结清不阻止日结，日结不自动结清现金，取消沿用回退。保留原因：关闭账目与实际现金发放是独立状态。
- 预览检查待付款、小费未确认、付款差额、缺结束；手动改价为非阻塞提醒，普通日结可通过，强制需原因。保留原因：`ClosingsService` 的五项检查没有旧文档额外的负数检查，负数由输入/数据库约束处理。
- 记工页无阻塞可直接普通日结，有阻塞进入同店同日财务核对；异常可原地打开单笔，外部深链接仍可定位记工；取消按有效版本、不强制填写原因。保留原因：当前财务页已直接使用编辑弹窗，无需旧规则强制跳离页面。
- 自动日结按店铺时区每天 23:30 所在分钟执行，要求所有检查无异常（含改价提醒）；已日结/取消过跳过，离线错过不补历史，无记录也可结。保留原因：API 已有定时服务，旧“不自动日结”不成立，自动流程也不应强制跳过异常。
- 首次成功日结原子排队在职、开启接收、有有效号码且当天有记工的个人小结；已有 SENT/QUEUED/CLAIMED 跳过，取消再结不自动补发。保留原因：任务与账目必须共同提交，并避免日结前逐人发送造成重复。
- 管理者可在未日结时逐人发送当时快照，批量仍要求日结；队列可看进度并取消排队项，离线代理稍后领取。保留原因：独立逐人任务允许空日结外键，不能要求所有任务有有效周期。
- 个人日结只返回目标员工，已确认工资/小费按现金、非现金及合计展示，现金交接先于逐笔；图片随内容增长，待付款在逐笔标明。保留原因：工资隐私和收入确认范围需由后端保护，长图不能截掉记录。

## 经营分析与支出

- 经营分析仅 Owner/Manager，全店、默认全部历史，支持七天、三十天、本月及自定义范围，不继承财务筛选。保留原因：经营趋势与个人工资查询有不同权限和范围。
- 小时/星期热图按历史开始时间及保存时区分组，首尾空小时裁掉、中间补零；每日记工含待付款，跑客人数独立堆叠，仅跑客日也纳入。保留原因：加项/卖卡不增加服务笔数，设备当前时区不能重写历史分组。
- 营业额为折后服务加卖卡实收、不含小费，未日结为缺口；星期平均按已日结天数，七日均线纳入起日前六天、仅已日结样本，显示样本数。保留原因：未结日不是零样本，窗口与筛选边界不同。
- 支出仅管理者，独立自然月查询，可补历史或未来月、已日结也可录；不自动导入工资、手续费、礼卡核销，不改原收入/工资公式。保留原因：`ExpensesService` 是独立账目，日结不锁支出。
- 支持一次性、固定/预算的每 X 天或 X 月周期；月周期从月首、按整月均分，天周期按覆盖日期分摊，余数归较早单位；日均除整月自然天数。保留原因：分摊总额必须等于整期美分，本月未结束也不能改变分母。
- 实际账单覆盖整期、可零，撤销恢复默认预算/固定值；预算标为估算。保留原因：跨月账单不能重复覆盖或把零账单误当未录。
- 规则前向追加，从后续周期起点生效；停止不截断已开周期，重启不早于停止，允许间隔；未来已录实际账单须先撤销相关覆盖，历史纠错用单期覆盖。保留原因：改规则不能悄悄隐藏既有账单或重写更早周期。
- 名称/备注及一次性日期金额可编辑，软删除排除所有月、恢复重纳入，规则与覆盖共享项目版本、幂等与审计。保留原因：同项目的并发规则和账单编辑必须互相冲突而不是覆盖。

## 实时、AI 与产品边界

- SSE 通知重读 REST，正常约二至三秒加请求耗时；保留日期、滚动与草稿，隐藏/离线暂停、恢复补读；十秒无消息重连，失败低频重试。保留原因：事件不是账本，连接成功也不代表数据已同步。
- “已同步”需实际消息/心跳及最近 REST 成功，连续变化合并、读取中变化排队；旧请求在切店/卸载失效。保留原因：失败读取或过期响应不能覆盖新上下文。
- Web AI 先理解、保存完整服务器预览、用户确认、重新鉴权并一次消费；详情、付款、审计与预览消费同事务，删除二次确认。保留原因：模型不能直接授予权限或执行任意 SQL。
- 会话按店铺、用户和助手隔离，历史帮助理解追问、财务重新查最新数据；权限变化不沿用旧范围，前端刷新不自动恢复会话。保留原因：历史回复和未执行预览都不是本次写入或财务事实。
- AI 财务只调用确定性统计并解释，员工仅本人，管理者仅本店；模型未配置仍可手工记工及查账。保留原因：核心业务与外部模型可用性独立。
- 语音每段六至六十秒、最多 8 MB，转写可修改后发送，录音只在请求内存流转；不可用时文字/系统听写。保留原因：当前供应商和浏览器能力有边界，原始录音不进入账目存储。
- 微信机器人规则集中在 [机器人手册](../operations/LANGBOT_WORK_BOT.md)：实时目录、原文证据、绑定身份与受限意图；多人同事务，澄清只学习。保留原因：插件和 Web 的确认流程不同，不能复制成同一条预览政策。
- Web 不注册 Service Worker、不提供安装入口、不持久缓存业务响应；只保留偏好及限时未提交草稿。保留原因：离线旧账和敏感缓存会误导写入及共用设备用户。
- 预约、房间/排钟、客户档案、软件收款、余额核销、库存、退款专项、自动转账、工资税/报税及共用设备 PIN 不属于现有实现。保留原因：清理不扩展产品范围，也不能把初版计划写成已交付功能。
